# رودمپ ۲.۰ Hero — شرکت نرم‌افزاری چندتیمی

وضعیت: `در حال بازطراحی` — مبنا: 2026-08-30

## نتیجهٔ مورد نظر

مالک یک مسئلهٔ سادهٔ فارسی می‌دهد. Hero مسئله را به محصول و Task Graph تبدیل می‌کند، تیم مناسب را با قرارداد روشن انتخاب می‌کند، هر تیم در مرز خودش کار می‌کند، ورودی و خروجی در گیت‌های تعیین‌شده بررسی می‌شوند و نتیجه با شواهد قابل تحویل ارائه می‌شود.

```text
درخواست مالک
  -> فهم و تصمیم محصول
  -> تشکیل تیم پروژه
  -> اجرای مرحله‌ای/خودکار طبق سیاست
  -> بررسی ورودی و خروجی هر تیم
  -> بازکاری یا ادامه
  -> کیفیت، امنیت و عملیات
  -> تحویل و یادگیری
```

## وضعیت خط مبنا

- قراردادهای HERO-001 تا HERO-019 و Harnessهای deterministic موجودند و آخرین اجرای محلی 143 تست موفق داشته است.
- HERO-020 هنوز به شواهد واقعی Clean Linux، Compose و Restore نیاز دارد.
- HERO-021 هنوز پایلوت واقعی Provider/اپلیکیشن نیست و به‌صورت پیش‌نویس طراحی باقی مانده است.
- در این بازنگری، کاتالوگ ۱۱ تیم شیت، قرارداد تیم، Registry، Eventهای تیم و API/نمایش اولیهٔ کنترل تیم اضافه شده‌اند.
- اصول حیاتی Hero/محصول و Release Promotion از Git تا test و تأیید production نیز به‌صورت قرارداد و گیت deterministic اضافه شده‌اند.
- این پیاده‌سازی هنوز in-memory است؛ هیچ Provider زنده، هزینه، Secret، deploy یا پیام خارجی فعال نشده است.

## نقشهٔ مرحله‌ای

### مرحلهٔ ۰ — حاکمیت و خط مبنا

وضعیت: `موجود`

HERO-001 تا HERO-021، منشور، Authorization Snapshot، Global Stop، Clean-room، Runner، Planner، Quality Gate، Assurance و Portability قرارداد پایه را می‌سازند.

معیار عبور: اسناد نسخه‌دار، تست و شواهد واقعی؛ HERO-020 و HERO-021 تا زمان رفع پیش‌نیازها Done محسوب نمی‌شوند.

### مرحلهٔ ۱ — کاتالوگ و قرارداد تیم‌ها

وضعیت: `انجام‌شده در این بازنگری`

- ثبت ۱۱ تیم شیت با `teamId` پایدار؛
- تعریف مسئولیت، اختیار، ورودی، خروجی، اصول، همکاران، مراحل و حالت پیش‌فرض؛
- تعریف وضعیت‌های تیم، هدف‌های بررسی، حالت‌های خودکارسازی، وضعیت آموزش و وضعیت تخصیص؛
- افزودن اعتبارسنجی و تست‌های قرارداد.

معیار پذیرش: هر ۱۱ تیم قابل فهرست، بدون تعریف ناقص و بدون نام‌گذاری مبهم باشند.

### مرحلهٔ ۲ — اتاق کنترل تیم

وضعیت: `هستهٔ اولیه انجام‌شده؛ تکمیل عملیاتی باقی‌مانده`

- Registry نسخه‌دار و Event Log برای بررسی قرارداد، بازکاری، آموزش، تخصیص و تغییر اختیار؛
- کنترل owner-gated برای تأیید/رد قرارداد و خروجی؛
- API و نمایش فارسی برای مشاهدهٔ تیم‌ها و تأیید/بازکاری بخش‌های قرارداد؛
- idempotency و جلوگیری از ثبت تکراری فرمان؛
- ثبت فلو پروژه و وضعیت کار تیم.

انجام‌شده در این گام: مرز احراز هویت signed-session مالک برای `/api/*`، تست fail-closed، migration اولیهٔ PostgreSQL، Runner migration و Event Store تراکنشی تزریق‌پذیر.
باقی‌مانده: اتصال پایدار به PostgreSQL، session revocation، pagination/audit view، ثبت diff قرارداد و نمایش timeline کامل.

### مرحلهٔ ۲.۵ — اصول حیاتی و گیت انتشار

وضعیت: `قرارداد و هستهٔ deterministic انجام‌شده؛ Adapter عملیاتی باقی‌مانده`

- اصول پایهٔ Hero به‌صورت inherited برای هر محصول اعمال می‌شوند؛ محصول می‌تواند اصول اختصاصی نسخه‌دار تعریف کند؛
- اصل تأییدنشده یا ردشده در control point مربوط blocking است و مالک می‌تواند تأیید، رد یا بازکاری کند؛
- Release با Artifact ID، SemVer و commit SHA ثبت می‌شود؛
- مسیر اجباری `test-deployment → test-evidence → owner approval → explicit production command` اضافه شده است؛
- تطبیق دقیق Artifact/version/commit و نیاز به مجوز جداگانهٔ `production-deploy` enforce می‌شود؛
- محیط‌های test و production از نظر مدل داده و وضعیت جدا هستند؛ Deployment Adapter زنده هنوز غیرفعال است.

معیار عبور: برای یک Release، تست ناموفق یا Artifact متفاوت باید production را fail-closed متوقف کند و مسیر rollback ثبت‌پذیر باشد.

### مرحلهٔ ۳ — توانمندسازی و آموزش تیم

وضعیت: `بعدی`

- آموزش پنج‌گانهٔ mission، safety، output-contract، collaboration و quality؛
- کتابخانهٔ درس و الگوی حل مسئله برای هر تیم؛
- آزمون ورودی/خروجی، امتیاز مهارت و ارزیابی دوره‌ای؛
- مقایسهٔ خروجی تیم با معیار طلایی و ثبت برنامهٔ بهبود؛
- ارتقای نسخهٔ توانمندی بدون تغییر خاموش منشور.

معیار عبور: تیم فقط پس از قبولی همهٔ ماژول‌ها و داشتن Artifact ارزیابی‌شده، `ready` شود.

### مرحلهٔ ۴ — تشکیل تیم پروژه و تخصیص هوشمند

وضعیت: `قرارداد مسیر‌یابی افزوده شد؛ اتصال Registry باقی است`

- Planner اکنون برای هر Task تیم مالک، تیم‌های همکار، مرحله و approval mode را پیشنهاد و در Event ثبت می‌کند؛
- اتصال این پیشنهاد به readiness و ظرفیت TeamRegistry هنوز باید تکمیل شود؛
- راهبرو تخصیص را با یک تیم مالک اصلی و همکاران مشخص ثبت کند؛
- ورودی تیم از Artifact نسخه‌دار قبلی ساخته شود؛
- تداخل فایل، منبع و ظرفیت پیش از اجرا شناسایی شود؛
- مالک بتواند تخصیص را تأیید، رد، جابه‌جا یا برای بازکاری برگرداند.

معیار عبور: هیچ Task بدون تیم مالک، قرارداد ورودی و سیاست approval قابل dispatch نباشد.

### مرحلهٔ ۵ — اجرای واقعی در مرز تیم

وضعیت: `بعدی و وابسته به HERO-020`

- اتصال Adapterهای Provider پشت قرارداد تیم/Task؛
- اجرای هر تیم در Worktree/Runner ایزوله؛
- context حداقلی و متناسب با نقش تیم؛
- ثبت start، checkpoint، evidence، handoff و stop در Event Log؛
- عدم جعل خروجی در صورت نبود Provider یا زیرساخت.

معیار عبور: یک Task واقعی در محیط Linux پاک، با شواهد اجرای واقعی و بدون Secret در repository یا Sheet.

### مرحلهٔ ۶ — حلقهٔ کیفیت، رد/بازکاری و تحویل

وضعیت: `قرارداد پایه موجود؛ اتصال تیمی باقی‌مانده`

- تسترو و امینتو به‌عنوان گیت‌های مستقل کیفیت و امنیت؛
- خروجی ردشده به همان تیم یا تیم مسئول برگردد، همراه با feedback و نسخهٔ جدید؛
- سقف چرخهٔ بازکاری، هزینهٔ policy unit و Global Stop اعمال شود؛
- راهبرو فقط پس از گیت‌ها بستهٔ تحویل را ببندد؛
- محصولو نتیجهٔ کسب‌وکاری و داده‌و KPI پس از تحویل را دنبال کنند.

معیار عبور: مسیر `output -> rejected -> rework -> retest -> approved` با شواهد و قابلیت replay قابل مشاهده باشد.

### مرحلهٔ ۷ — شرکت کامل و عملیات پایدار

وضعیت: `پیشنهادی`

- افزودن توانمندسازو به‌عنوان تیم رسمی آموزش و ارزیابی؛
- افزودن رشد و پشتیبان برای feedback و پشتیبانی کاربر؛
- افزودن مالی و حقوقی برای هزینه، قرارداد و انطباق؛
- ظرفیت‌سنجی، بودجه، SLA، رخداد، Backup/Restore و گزارش دوره‌ای؛
- داشبورد portfolio برای چند پروژه و چند تیم هم‌زمان.

این مرحله بدون مجوز جداگانه، هیچ خرید، پرداخت، پیام بیرونی، قرارداد یا تغییر Secret انجام نمی‌دهد.

### مرحلهٔ ۸ — پایلوت واقعی HERO-021

وضعیت: `مسدود تا رفع گیت‌ها`

پایلوت با یک محصول کوچک واقعی، یک پلتفرم مشخص و معیار پذیرش روشن اجرا می‌شود. پیش‌نیازها: HERO-020 کامل، Linux/Docker/Compose جدا، Provider واقعی با دسترسی کنترل‌شده و مجوز مستقل عملیات حساس. موفقیت فقط با Artifact، test evidence، review، handoff و گزارش تحویل اعلام می‌شود.

## گیت‌های تصمیم مالک

مالک در هر پروژه چهار انتخاب مستقل دارد:

| تصمیم | دامنه |
| --- | --- |
| قرارداد تیم | تأیید/رد مسئولیت، اختیار، ورودی، خروجی، اصول و فلو |
| نحوهٔ همکاری | هر گام، فقط گیت‌ها یا خودکار تا زمان ریسک |
| بازکاری | هدف، feedback، روش جایگزین، تیم مسئول و نسخهٔ خروجی جدید |
| ساختار سازمان | ادغام، تفکیک، تغییر مالکیت یا افزودن تیم مکمل |

هیچ‌کدام از این انتخاب‌ها به‌صورت ضمنی مجوز Production، هزینه، Secret، حذف داده، پیام خارجی یا عملیات برگشت‌ناپذیر ایجاد نمی‌کند.

## تعریف Done در رودمپ جدید

هر مرحله باید علاوه بر Definition of Done فعلی، این موارد را داشته باشد:

- قرارداد تیم و نسخهٔ سند مشخص؛
- ورودی و خروجی با Artifact ID و نسخه؛
- owner decision یا policy صریح برای گیت؛
- Eventهای append-only و idempotency؛
- نتیجهٔ آموزش/تست/بازبینی قابل بازتولید؛
- مسیر بازکاری و rollback/recovery؛
- وضعیت صریح `blocked` در نبود Provider، محیط یا مجوز؛
- ثبت وضعیت در Google Sheet مدیریت پروژه پس از شواهد واقعی.

## مواردی که هنوز نباید Done اعلام شوند

1. اتصال واقعی ChatGPT/Codex/Claude/Cursor؛
2. ساخت اپلیکیشن واقعی برای یک درخواست مالک؛
3. اتصال PostgreSQL عملیاتی و queue/outbox durable؛ migration boundary فعلاً آماده و بدون اتصال زنده است؛
4. Clean Linux backup/restore با checksum؛
5. Preview، cloud build، deploy، secret management و external spend؛
6. آموزش مبتنی بر benchmark واقعی تیم‌ها؛
7. داشبورد کامل چندپروژه‌ای و timeline عملیاتی.

این موارد به‌ترتیب در مراحل ۳ تا ۸ می‌آیند و هر کدام باید Authorization و Evidence متناسب خود را داشته باشند.
