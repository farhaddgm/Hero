# صد گام بعدی Hero — فهرست اجرایی و وضعیت واقعی

مبنا: ۲۰۲۶-۰۹-۰۴ — شاخهٔ `codex/hero-001-project-charter`

این سند ۱۰۰ اقدام بعدی را ثبت می‌کند تا مسیر گم نشود. «باز» بودن یک اقدام الزاماً به معنی blocker فعلی نیست؛ وضعیت هر ردیف مشخص می‌کند اقدام اکنون قابل انجام است، به اقدام مالک/ادمین نیاز دارد، یا باید بعد از Test/Pilot انجام شود.

دامنهٔ رسمی Test طبق کد و مستندات فعلی `test.hero.beeproject.ir` است. نام `hero-test.beeproject.ir` نباید هم‌زمان استفاده شود مگر اینکه همهٔ کد، DNS، Caddy و مستندات یک‌جا تغییر کنند.

| ۱۰۰ | اجرای Production و review پس از انتشار | بعد از مجوز مستقل | ادمین + شما | فرمان صریح، مجوز `production-deploy` و post-release review |

## مواردی که فعلاً مانع هستند

برای استفادهٔ عملیاتی Test، مهم‌ترین blockerهای باقی‌مانده این‌ها هستند: اتصال host-level Runner به همین Task، دسترسی واقعی wrapperها، تعیین تکلیف `compose.test.yaml`، تصمیم رسمی دامنه/محیط و مالک عملیات، audit محل نگهداری Secret، مرور دستی DNS/TLS/Caddy و فعال‌سازی CI/reviewer. Compose و PostgreSQL مستقل Test و شواهد health/auth/UI اکنون موفق‌اند؛ preflight سخت‌گیرانه و persistence candidate جاری به‌علت دو Secret PostgreSQL هنوز تأیید نشده‌اند و recovery مقصد نیز گیت جدا دارد.

برای Pilot علاوه بر موارد بالا، درخواست واقعی، معیار پذیرش، Provider/Model، سقف هزینه و مجوز مستقل لازم است.

Production در این سند فقط به‌عنوان مسیر آینده آمده و از مجوز توسعه نتیجه‌گیری نمی‌شود.

## نتیجهٔ تحقیق و بنچ‌مارک فنی — ۲۰۲۶-۰۹-۰۵

### تصمیم‌های منتخب

۱. **Compose:** استفاده از project name صریح `hero-test` برای جداسازی روی میزبان مشترک مناسب است. Docker Compose نام پروژه را برای گروه‌بندی و جداسازی resourceها استفاده می‌کند و نام سرویس داخل شبکه از IP پایدارتر است؛ بنابراین PostgreSQL باید داخل شبکه با نام سرویس استفاده شود و پورت میزبان فقط برای دسترسی لازم منتشر شود. [Docker Compose project names](https://docs.docker.com/compose/how-tos/project-name/) و [Compose networking](https://docs.docker.com/compose/how-tos/networking/)

۲. **Test isolation:** قرارداد فعلی `127.0.0.1:43101`، volumeهای project-scoped و PostgreSQL بدون host port با این الگو هم‌راستا است. فایل یا alias دیگری مانند `compose.test.yaml` فقط بعد از بررسی، مالکیت روشن و ثبت نسخه‌دار قابل استفاده است.

۳. **Caddy:** مسیر Test باید با `reverse_proxy` به `127.0.0.1:43101` برسد. Basic Auth باید فقط با password hash‌شده ذخیره شود؛ پیش از reload، کل config واقعی Caddy باید validate شود. [Caddy reverse_proxy](https://caddyserver.com/docs/caddyfile/directives/reverse_proxy)، [Caddy basic_auth](https://caddyserver.com/docs/caddyfile/directives/basic_auth)، و [Caddy command line](https://caddyserver.com/docs/command-line)

۴. **CI و Secret:** GitHub Environment می‌تواند required reviewer، محدودیت branch/tag و Secretهای محیطی داشته باشد؛ Secretهای محیط فقط پس از عبور protection rule در اختیار job قرار می‌گیرند. چون self-hosted runner محیط کانتینری ایزوله محسوب نمی‌شود، Runner باید فقط scope لازم Hero را داشته باشد. [GitHub deployments and environments](https://docs.github.com/en/actions/reference/workflows-and-actions/deployments-and-environments)

۵. **Backup/Restore:** برای Test از PostgreSQL custom-format archive (`pg_dump -Fc`) و restore در database/volume جدا استفاده شود؛ این قالب برای `pg_restore` مناسب است و امکان بررسی artifact قبل از جایگزینی را می‌دهد. [PostgreSQL pg_dump](https://www.postgresql.org/docs/17/app-pgdump.html)

### نتیجهٔ تصمیم معماری

بهترین مسیر فعلی این است: **همان سرور، ولی محیط Test کاملاً project-scoped، پورت loopback، Secret جدا، Runner محدود، Caddy با تغییر حداقلی و Production کاملاً جدا**. VM جدا از نظر ریسک بهتر است، اما تا وقتی Runner و wrapper واقعی آماده نباشد، فقط نام VM مشکل دسترسی را حل نمی‌کند.

این بنچ‌مارک، اجرای Provider واقعی، هزینه، تغییر Secret و Production را مجاز نمی‌کند؛ این موارد همچنان گیت مستقل دارند.
