## هدف و جایگاه

Hero برای یک مالک تصمیم‌گیر طراحی شده است؛ پس هر وضعیت باید «چرا» داشته باشد، هر تصمیم از موبایل ممکن باشد و دوزبانگی فقط دو صفحه نماند. این مسیر شکاف‌های UX باقی‌ماندهٔ BO-UX-001..004 را با کنترل‌های قابل‌سنجش می‌بندد.

این سند کارت ۱۰ گام این مسیر را نگه می‌دارد. نمای کلی، موج‌ها، مسیر بحرانی و مرز مجوز در [پنجاه گام جدید توسعهٔ Hero](../roadmap/NEXT-50-STEPS-20261013.md) است؛ فهرست ماشینی در `config/product-development/next-50-steps-v1.json` است و `pnpm check:next-steps` هماهنگی آن‌ها را کنترل می‌کند.

## قواعد مشترک همهٔ کارت‌ها

- وضعیت همهٔ گام‌ها `proposed` است: الزام‌آور یا مجاز به اجرا نیستند. پیش از Dispatch باید Snapshot مجوز نسخه‌دار با Step ID و نسخهٔ همین سند ثبت شود و Global Stop خاموش باشد (AGENTS.md قاعدهٔ ۱۱).
- تغییر محتوای یک کارت نسخهٔ این سند را بالا می‌برد و مجوزهای ثبت‌شده برای نسخهٔ قبلی را بی‌اثر می‌کند.
- «معیار پذیرش» شرط لازم برای `source_complete` است؛ `verified` فقط با گیت همان کارت (ستون «گیت تأیید») و Evidence واقعی ممکن است.
- هیچ کارتی مجوز Provider زنده، هزینهٔ بیرونی، تغییر Secret، Production، حذف داده یا پیام بیرونی نیست؛ این‌ها جداگانه گیت دارند (AGENTS.md قاعدهٔ ۱۲).

## کارت گام‌ها

### NX-031 — گسترش دوزبانگی به همهٔ صفحات

| ویژگی | مقدار |
|---|---|
| موج | 2 |
| اولویت | P1 |
| اندازه | L |
| گیت تأیید | `test-runtime` |
| وابستگی | `NX-016`، `BO-UX-001` |
| وضعیت | `proposed` |

**مسئله.** `ui-locale.mjs` (BO-149) فارسی و انگلیسی دارد ولی فقط دو نما (Inbox و Help) از `createTranslator` استفاده می‌کنند و ۱۲ فایل نمای دیگر متن را مستقیم دارند؛ BO-UX-001 هنوز partial است. متن‌های مختلط (شناسه، digest، URL درون متن راست‌به‌چپ) جهت‌دهی منظم ندارند.

**خروجی‌ها**
- استخراج تدریجی متن به کاتالوگ پیام
- گیت برابری کلیدها (هر کلید در هر دو زبان)
- ایزوله‌سازی bidi برای توکن‌های LTR و گزارش پوشش ترجمه به‌ازای صفحه

**معیار پذیرش**
- هر کلید کاتالوگ در fa و en هست
- شناسه‌های data-*، route و enum تغییر نمی‌کنند
- `ui-static-audit` برای هر دو زبان `lang` و `dir` درست را تأیید می‌کند
- گزارش پوشش، درصد واقعی را می‌گوید نه ادعای ۱۰۰٪

**مرز.** موجی؛ صفحه‌ای که مهاجرت نشده در گزارش «مهاجرت‌نشده» ثبت می‌شود.

### NX-032 — جست‌وجوی سراسری فراتر از ناوبری

| ویژگی | مقدار |
|---|---|
| موج | 3 |
| اولویت | P2 |
| اندازه | M |
| گیت تأیید | `test-runtime` |
| وابستگی | `NX-016`، `NX-031` |
| وضعیت | `proposed` |

**مسئله.** پالت Ctrl+K در `hero-shell.mjs` فقط فهرست ثابت صفحه‌ها را فیلتر می‌کند (با نرمال‌سازی فارسی)؛ پیدا کردن یک پروژه، Run، سند یا تصمیم هنوز با ناوبری دستی است.

**خروجی‌ها**
- ایندکس سمت سرور فقط از داده‌ی مجاز برای نشست (project-scoped)
- همان نرمال‌سازی فارسی مشترک (NX-016)
- دسته‌بندی نتایج، پیمایش با صفحه‌کلید و audit خواندن

**معیار پذیرش**
- Viewer نتیجه‌ای از پروژهٔ فاقد grant نمی‌بیند (آزمون HTTP چندپروژه‌ای)
- محتوای حساس (Secret، متن Conversation) در ایندکس نیست
- «ي/ی» و «۱/1» یکی گرفته می‌شوند
- پالت فعلی regress نمی‌کند

**مرز.** جست‌وجوی متن کامل محتوای خصوصی خارج دامنه است.

### NX-033 — توضیح‌دهندهٔ «چرا؟» برای هر وضعیت

| ویژگی | مقدار |
|---|---|
| موج | 2 |
| اولویت | P1 |
| اندازه | M |
| گیت تأیید | `test-runtime` |
| وابستگی | `ADR-0005`، `BO-UX-003` |
| وضعیت | `proposed` |

**مسئله.** BO-UX-003 می‌گوید «چرا» و drill-down هنوز برای همهٔ شمارنده‌ها و وضعیت‌ها یکسان نیست؛ کاربر «مسدود» را می‌بیند ولی نه این‌که کدام گیت، کدام Step ID/نسخهٔ مجوز و چه کسی باید اقدام کند.

**خروجی‌ها**
- زنجیرهٔ دلیل ماشینی (gate ← علت ← اقدام‌کننده ← پیوند Evidence) برای وضعیت‌های blocked/pending/stale
- متن ساده فارسی تولیدشده از کدهای دلیل، نه متن آزاد
- جزء مشترک برای صفحه‌ها

**معیار پذیرش**
- هر کد دلیل موجود در domain یک متن ساده دارد (آزمون پوشش)
- دلیل «نامشخص» صریحاً نمایش داده می‌شود، نه حذف
- هیچ Secret یا متن خصوصی در دلیل نیست

**مرز.** فقط توضیح می‌دهد؛ هیچ گیتی را باز یا دور نمی‌زند.

### NX-034 — کارت‌های تأیید موبایل‌محور

| ویژگی | مقدار |
|---|---|
| موج | 3 |
| اولویت | P2 |
| اندازه | M |
| گیت تأیید | `test-runtime` |
| وابستگی | `NX-033`، `BO-UX-002` |
| وضعیت | `proposed` |

**مسئله.** BO-UX-002 می‌گوید هدف‌های Desktop-first رسمی نشده‌اند؛ تصمیم‌های فوری مالک (تأیید/رد در Inbox) باید روی موبایل با کمترین خطا ممکن باشد.

**خروجی‌ها**
- نمای تک‌ستونی با هدف‌های لمسی بزرگ
- خلاصهٔ گره‌خورده به digest دقیق چیزی که تأیید می‌شود
- تأیید مجدد (MFA تازه) برای اقدام پرریسک و جلوگیری از دوبار-تپ

**معیار پذیرش**
- آزمون مرورگر در viewport ‏۳۶۰×۷۸۰: بدون اسکرول افقی و با هدف لمسی ≥ ۴۴px
- تأیید بدون digest مطابق رد می‌شود
- ریسک بالا بدون MFA تازه رد می‌شود

**مرز.** منطق تأیید سرور تغییر نمی‌کند؛ فقط نمای دیگری روی همان فرمان‌هاست.

### NX-035 — خلاصهٔ روزانهٔ مالک

| ویژگی | مقدار |
|---|---|
| موج | 3 |
| اولویت | P1 |
| اندازه | M |
| گیت تأیید | `test-runtime` |
| وابستگی | `AR-05`، `NX-033` |
| وضعیت | `proposed` |

**مسئله.** تصمیم‌ها، هزینه، حادثه و شکاف تحویل در چند صفحه پخش است؛ مالک برای دانستن «امروز چه چیزی منتظر من است» چند صفحه می‌گردد.

**خروجی‌ها**
- صفحه/endpoint خلاصه برای ۲۴ ساعت اخیر: تصمیم‌های منتظر، تغییر گیت‌ها، هزینه نسبت به سقف، حوادث، شکاف Delivery Truth
- نمای قابل‌چاپ
- بدون ارسال بیرونی

**معیار پذیرش**
- هر عدد خلاصه با شمارندهٔ صفحهٔ مبدأ برابر و پیوند drill-down دارد (قاعدهٔ BO-UX-003)
- داده‌ٔ کهنه برچسب تازگی دارد
- فقط نقش مجاز می‌بیند؛ ایمیل/پیام ارسال نمی‌شود

**مرز.** ارسال ایمیل/پیام بیرونی خارج دامنه و نیازمند مجوز جدا است.

### NX-036 — چک‌لیست راه‌اندازی اولیهٔ هدایت‌شده

| ویژگی | مقدار |
|---|---|
| موج | 3 |
| اولویت | P2 |
| اندازه | S |
| گیت تأیید | `test-runtime` |
| وابستگی | `NX-031` |
| وضعیت | `proposed` |

**مسئله.** راهنما و Walkthrough وجود دارد، ولی مالک جدید نمی‌داند کدام اقدام‌ها (ثبت MFA، ساخت پروژه، تعیین Provider پیش‌فرض، سیاست هزینه) هنوز انجام نشده‌اند.

**خروجی‌ها**
- چک‌لیست نقش‌محور که وضعیت هر آیتم را از state واقعی تشخیص می‌دهد (نه کلیک «انجام شد»)
- پیشرفت per-user
- پیوند مستقیم به صفحهٔ اقدام؛ دوزبانه

**معیار پذیرش**
- آیتم فقط وقتی کامل است که state واقعی آن را نشان دهد
- Viewer فقط آیتم‌های مربوط به خود را می‌بیند
- هر دو زبان پوشش دارند

**مرز.** هیچ اقدامی را به‌جای کاربر انجام نمی‌دهد.

### NX-037 — گزارش انطباق دسترس‌پذیری (WCAG 2.2 AA)

| ویژگی | مقدار |
|---|---|
| موج | 1 |
| اولویت | P1 |
| اندازه | M |
| گیت تأیید | `offline` |
| وابستگی | — |
| وضعیت | `in_progress` |

**مسئله.** ممیزی ایستای RTL/a11y و `ui-browser-audit` وجود دارند، اما خروجی آن‌ها به معیارهای WCAG 2.2 AA نگاشت نشده؛ نمی‌شود گفت کدام معیار با چه شواهدی پوشش دارد و کدام فقط به بررسی انسانی نیاز دارد.

**خروجی‌ها**
- ماتریس معیار↔آزمون/شواهد
- مولد گزارش به‌ازای صفحه
- معیارهای نیازمند بررسی انسانی با وضعیت `needs-human` (نه pass) و checker ناهمخوانی ماتریس با آزمون‌ها

**معیار پذیرش**
- معیاری بدون هیچ آزمون خودکار هرگز `pass` نمی‌شود
- حذف آزمونی که ماتریس به آن ارجاع داده checker را fail می‌کند
- گزارش، درصد پوشش خودکار را بدون بزرگ‌نمایی می‌دهد

**مرز.** گواهی انطباق نیست؛ ابزار شفاف‌سازی پوشش است.

### NX-038 — ترجیحات اعلان و ساعت سکوت

| ویژگی | مقدار |
|---|---|
| موج | 2 |
| اولویت | P2 |
| اندازه | S |
| گیت تأیید | `test-runtime` |
| وابستگی | `BO-NTF-002` |
| وضعیت | `proposed` |

**مسئله.** اعلان‌ها SLA، dedup و گروه‌بندی حادثه دارند، اما هر کاربر کنترل ساعت سکوت یا خلاصه‌سازی ندارد؛ اعلان زیاد باعث بی‌توجهی می‌شود.

**خروجی‌ها**
- ترجیح per-user برای ساعت سکوت، تجمیع digest و آستانهٔ شدت
- کف غیرقابل‌تضعیف: اعلان بحرانی و نیازمند تصمیم هرگز پنهان نمی‌شود
- فقط کانال داخلی

**معیار پذیرش**
- تنظیم کاربر نمی‌تواند اعلان `critical` را حذف کند
- ساعت سکوت فقط نمایش را به تأخیر می‌اندازد و SLA ثبت‌شده را تغییر نمی‌دهد
- تغییر ترجیح audit می‌شود

**مرز.** کانال بیرونی (ایمیل/پیام‌رسان) خارج دامنه است.

**ورودی لازم از مالک.** مقدار پیش‌فرض ساعت سکوت

### NX-039 — دفتر تصمیم و پیش‌نویس ADR

| ویژگی | مقدار |
|---|---|
| موج | 2 |
| اولویت | P2 |
| اندازه | S |
| گیت تأیید | `offline` |
| وابستگی | — |
| وضعیت | `proposed` |

**مسئله.** تصمیم‌های مالک در `/api/ai/decisions` و Proposalها ثبت می‌شوند، اما تبدیل آن‌ها به ADR مستند در Git دستی است و تصمیم‌های مهم ممکن است هرگز مستند نشوند.

**خروجی‌ها**
- تولیدکنندهٔ پیش‌نویس ADR (Markdown از `docs/templates/ADR.md`) از تصمیم حل‌شده با پیوند Evidence و وضعیت `proposed`

**معیار پذیرش**
- پیش‌نویس از قالب موجود و بدون Secret ساخته می‌شود
- هرگز خودکار commit یا در رجیستری ثبت نمی‌شود
- تصمیم ردشده یا معلق پیش‌نویس `active` نمی‌سازد

**مرز.** مستندسازی نهایی با انسان و review است.

### NX-040 — بازنگری Run و پیشنهاد درس‌آموخته

| ویژگی | مقدار |
|---|---|
| موج | 4 |
| اولویت | P2 |
| اندازه | M |
| گیت تأیید | `test-runtime` |
| وابستگی | `NX-005`، `NX-006` |
| وضعیت | `proposed` |

**مسئله.** پس از هر Run نه علت بازکاری، نه هزینه و نه نقاط شکست به دانش تیم برنمی‌گردد؛ مسیر پیشنهاد دانش با تأیید مالک (team-research) هست ولی از Runها تغذیه نمی‌شود.

**خروجی‌ها**
- گزارش بازنگری از ردگیری redacted (NX-005): مراحل بازکاری، رد/تأییدهای Gateway، هزینه
- پیشنهاد دانش/اصل با منشأ `agent-derived` در قرنطینهٔ NX-006
- ورود به تیم فقط با تأیید مالک

**معیار پذیرش**
- پیشنهاد بدون Evidence ردگیری ساخته نمی‌شود
- پیشنهاد تأییدنشده هرگز وارد دانش تیم نمی‌شود
- محتوای خام prompt/خروجی در گزارش نیست

**مرز.** تغییر اصول حیاتی یا قرارداد تیم بدون تأیید مالک ممنوع است.
