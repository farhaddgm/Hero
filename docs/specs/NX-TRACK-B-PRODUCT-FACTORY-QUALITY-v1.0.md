## هدف و جایگاه

ماموریت Hero تبدیل ایده به محصول است. این مسیر حلقه‌های «ایده → معیار پذیرش قابل‌چک → محصول → حکم تمام‌شدن» را محکم می‌کند: معیار پذیرش ماشینی، امتیاز کامل‌بودن Intake، بستهٔ امنیت و مجوز برای محصول تولیدشده، کیت RTL و ابزار محلی‌سازی فارسی.

این سند کارت ۱۰ گام این مسیر را نگه می‌دارد. نمای کلی، موج‌ها، مسیر بحرانی و مرز مجوز در [پنجاه گام جدید توسعهٔ Hero](../roadmap/NEXT-50-STEPS-20261013.md) است؛ فهرست ماشینی در `config/product-development/next-50-steps-v1.json` است و `pnpm check:next-steps` هماهنگی آن‌ها را کنترل می‌کند.

## قواعد مشترک همهٔ کارت‌ها

- وضعیت همهٔ گام‌ها `proposed` است: الزام‌آور یا مجاز به اجرا نیستند. پیش از Dispatch باید Snapshot مجوز نسخه‌دار با Step ID و نسخهٔ همین سند ثبت شود و Global Stop خاموش باشد (AGENTS.md قاعدهٔ ۱۱).
- تغییر محتوای یک کارت نسخهٔ این سند را بالا می‌برد و مجوزهای ثبت‌شده برای نسخهٔ قبلی را بی‌اثر می‌کند.
- «معیار پذیرش» شرط لازم برای `source_complete` است؛ `verified` فقط با گیت همان کارت (ستون «گیت تأیید») و Evidence واقعی ممکن است.
- هیچ کارتی مجوز Provider زنده، هزینهٔ بیرونی، تغییر Secret، Production، حذف داده یا پیام بیرونی نیست؛ این‌ها جداگانه گیت دارند (AGENTS.md قاعدهٔ ۱۲).

## کارت گام‌ها

### NX-011 — کامپایلر معیار پذیرش

| ویژگی | مقدار |
|---|---|
| موج | 1 |
| اولویت | P0 |
| اندازه | M |
| گیت تأیید | `offline` |
| وابستگی | — |
| وضعیت | `source_complete` |

**مسئله.** قالب‌های محصول معیار پذیرش دارند و پیش‌نیاز پنجم Golden Path تأیید آن‌ها توسط مالک است، اما معیارها متن آزادند و مسیری آن‌ها را به بررسی ماشینی تبدیل نمی‌کند؛ «پذیرش» هنوز قضاوت دستی است.

**خروجی‌ها**
- قالب ساخت‌یافتهٔ معیار فارسی «وقتی … آنگاه …» با شناسهٔ پایدار
- کامپایلر قطعی به چک‌لیست ماشینی و اسکلت آزمون برای Product Runner
- معیار ناکامپایل‌شدنی `needs-clarification` می‌شود (نه pass)؛ شمارندهٔ پوشش «چند معیار قابل‌چک است»

**معیار پذیرش**
- پنج قالب فعلی با معیار ساخت‌یافته بدون تغییر معنا کامپایل می‌شوند
- معیار مبهم یا بدون پیش‌شرط رد می‌شود
- دو بار اجرا خروجی یکسان
- کامپایلر خودش تأیید نمی‌کند؛ استفاده منوط به تأیید مالک است

**مرز.** اجرای آزمون‌های تولیدشده فقط در Product Runner ایزوله؛ کد تولیدشده داخل فرایند Hero اجرا نمی‌شود.

### NX-012 — امتیاز کامل‌بودن Intake

| ویژگی | مقدار |
|---|---|
| موج | 2 |
| اولویت | P1 |
| اندازه | S |
| گیت تأیید | `offline` |
| وابستگی | `NX-011` |
| وضعیت | `proposed` |

**مسئله.** Intake Advisor «نمی‌دانم» را درست «خیر» حساب نمی‌کند، ولی به مالک نمی‌گوید ورودی‌اش چقدر برای شروع آماده است و کدام پرسش بیشترین ابهام را می‌بندد.

**خروجی‌ها**
- امتیاز کامل‌بودن وزن‌دار بر ابعاد (هدف، کاربران، داده، ریسک، پذیرش، محدودیت)
- فهرست پرسش‌های رتبه‌بندی‌شده بر پایهٔ میزان کاهش ابهام
- آستانهٔ «آمادهٔ پیشنهاد Foundation»

**معیار پذیرش**
- ورودی یکسان امتیاز یکسان
- «نمی‌دانم» امتیاز را بالا نمی‌برد و هیچ‌گاه «خیر» حساب نمی‌شود
- آزمون برای هر پنج قالب
- گیت‌های مجوز بدون تغییر

**مرز.** توصیه است نه گیت؛ شروع پروژه به آن گره نمی‌خورد مگر مالک سیاست بگذارد.

### NX-013 — بستهٔ قالب‌های بازار فارسی

| ویژگی | مقدار |
|---|---|
| موج | 3 |
| اولویت | P2 |
| اندازه | M |
| گیت تأیید | `offline` |
| وابستگی | `NX-011`، `NX-014` |
| وضعیت | `proposed` |

**مسئله.** پنج قالب فعلی (سایت ایستا، سایت با فرم تماس، پنل CRUD، سرویس REST، اپ یادآور موبایل) برای نیازهای رایج کسب‌وکار فارسی‌زبان کافی نیست: فرم‌ساز و نظرسنجی، رزرو نوبت، فروشگاه ساده با پرداخت sandbox، گزارش‌گیر CSV.

**خروجی‌ها**
- ۴ تا ۵ قالب جدید در همان قالب `templates-v1`
- معیار پذیرش ساخت‌یافته (NX-011)، پرچم ریسک و دلیل ساختاری برای هر «خیر»
- قالب‌های دارای پرداخت یا پیام بیرونی صراحتاً gated

**معیار پذیرش**
- `check:product-templates` و تمرین Golden Path برای قالب‌های جدید PASS
- قالب بدون معیار پذیرش ساخت‌یافته یا بدون ارزیابی ریسک ثبت نمی‌شود
- «ناشناخته» به «خیر» تبدیل نمی‌شود

**مرز.** فقط تعریف قالب؛ ساخت محصول واقعی، پرداخت واقعی و پیام بیرونی خارج دامنه است.

**ورودی لازم از مالک.** انتخاب و اولویت قالب‌ها

### NX-014 — بستهٔ پایهٔ امنیت محصول

| ویژگی | مقدار |
|---|---|
| موج | 2 |
| اولویت | P1 |
| اندازه | M |
| گیت تأیید | `offline` |
| وابستگی | `NX-007` |
| وضعیت | `proposed` |

**مسئله.** Quality Gate محصول را می‌سنجد، اما مجموعهٔ استانداردی از بررسی‌های امنیتی (هدرهای امنیتی، اعتبارسنجی ورودی، احراز هویت برای مسیرهای تغییردهنده، اسکن Secret، audit وابستگی از lockfile) برای هر محصول تولیدشده تعریف نشده و به ریسک محصول گره نخورده است.

**خروجی‌ها**
- فهرست نسخه‌دار بررسی‌ها با کلاس ریسک (محصول پرریسک بررسی‌های بیشتر)
- اجرای آفلاین در Product Runner
- ادغام نتیجه در Quality Gate با قاعدهٔ `unknown` ≠ pass

**معیار پذیرش**
- نمونهٔ مصنوعی ناایمن (بدون هدر، بدون احراز هویت، شبیه Secret) رد و نمونهٔ سالم PASS می‌شود
- audit وابستگی بدون شبکه از دادهٔ ثبت‌شده کار می‌کند و تازگی advisory را گزارش می‌دهد

**مرز.** ابزار اسکن بیرونی و پایگاه advisory زنده اتصال بیرونی است و گیت جدا دارد.

### NX-015 — کیت رابط RTL-first برای محصولات

| ویژگی | مقدار |
|---|---|
| موج | 2 |
| اولویت | P2 |
| اندازه | M |
| گیت تأیید | `offline` |
| وابستگی | `NX-016` |
| وضعیت | `proposed` |

**مسئله.** Hero برای رابط خودش tokenها و الگوهای RTL دارد (HERO-022)، اما قالب‌های وب محصول هر بار از صفر طراحی می‌شوند و کیفیت RTL و دسترس‌پذیری آن‌ها تضمین‌شده نیست.

**خروجی‌ها**
- tokenهای معنایی (رنگ، فاصله، تایپوگرافی) و ویژگی‌های logical CSS
- کامپوننت‌های پایه (دکمه، فرم، جدول، پیام وضعیت) با حالت‌های loading/empty/error
- مصرف در قالب‌های وب

**معیار پذیرش**
- ممیزی ایستا (مثل `ui-static-audit`) روی خروجی قالب‌ها: `dir="rtl"`، contrast ≥ 4.5، focus قابل‌مشاهده، بدون وابستگی CDN
- هیچ استایل با جهت فیزیکی (left/right) در کیت نیست مگر مستند
- وضعیت فقط با رنگ منتقل نمی‌شود

**مرز.** بدون وابستگی npm جدید؛ طراحی Back Office تغییر نمی‌کند؛ هر فایل قلم باید مجوز آزاد مستند داشته باشد.

### NX-016 — جعبه‌ابزار محلی‌سازی فارسی (جلالی، ارقام، ارز، جست‌وجو)

| ویژگی | مقدار |
|---|---|
| موج | 1 |
| اولویت | P1 |
| اندازه | S |
| گیت تأیید | `offline` |
| وابستگی | — |
| وضعیت | `source_complete` |

**مسئله.** نمایش تاریخ در UI به رفتار ضمنی `toLocaleDateString('fa-IR')` تکیه دارد و کتابخانهٔ صریح و آزمون‌پذیری برای تقویم جلالی در مخزن نیست، پس خروجی سمت سرور (گزارش، Evidence، خروجی چاپی) به ICU محیط وابسته است. همچنین `toPersianDigits` داخل ماژول domain به نام `delivery-truth` و `normalizeHeroSearch` در `ui-copy` مستقل نوشته شده‌اند و دو نسخهٔ نرمال‌سازی می‌توانند بی‌صدا ناهمخوان شوند.

**خروجی‌ها**
- ماژول خالص مشترک: تبدیل جلالی↔میلادی صریح با بردارهای آزمون شناخته‌شده، مستقل از ICU محیط
- قالب‌بندی عدد و ارز (ریال/تومان با قاعدهٔ صریح نمایش)
- استخراج و بازاستفادهٔ توابع فعلی نرمال‌سازی بدون تغییر رفتار

**معیار پذیرش**
- بردارهای رفت‌وبرگشت برای سال‌های کبیسه و مرز اسفند/فروردین
- آزمون‌های فعلی `ui-copy` و `delivery-truth` بدون تغییر پاس می‌شوند
- نرمال‌سازی با اصلاح ZWNJ در `content-safety` سازگار است

**مرز.** تبدیل ارز نمی‌کند، فقط نمایش؛ قواعد منطقهٔ زمانی خارج دامنه است.

### NX-017 — کارخانهٔ دادهٔ آزمون فارسی

| ویژگی | مقدار |
|---|---|
| موج | 2 |
| اولویت | P2 |
| اندازه | S |
| گیت تأیید | `offline` |
| وابستگی | `NX-016`، `BO-PRD-003` |
| وضعیت | `proposed` |

**مسئله.** آزمون‌های محصول به داده‌ٔ نمونهٔ واقع‌نما نیاز دارند و ساده‌ترین مسیر کپی‌کردن داده‌ٔ واقعی است که BO-PRD-003 صراحتاً ممنوع می‌کند.

**خروجی‌ها**
- تولیدکنندهٔ قطعی بر پایهٔ seed برای نام، نشانی، تلفن و شناسهٔ ملی‌شکل با الگوهای صریحاً مصنوعی
- برچسب `synthetic: true` در هر رکورد
- حفاظ: رکورد بدون این برچسب به مجموعهٔ آزمون وارد نمی‌شود

**معیار پذیرش**
- همان seed همان خروجی
- هیچ مقدار تولیدی از قالب شناسهٔ واقعی معتبر عبور نمی‌کند (آزمون checksum)
- رکورد بدون برچسب `synthetic` رد می‌شود

**مرز.** هیچ داده‌ٔ واقعی خوانده یا وارد نمی‌شود.

### NX-018 — گیت مجوز و وابستگی محصول

| ویژگی | مقدار |
|---|---|
| موج | 1 |
| اولویت | P1 |
| اندازه | M |
| گیت تأیید | `offline` |
| وابستگی | — |
| وضعیت | `proposed` |

**مسئله.** برای محصولات تولیدشده SBOM مرجع ثبت می‌شود (BO-OUT-003)، اما در کد فعلی هیچ گیتی سیاست مجوز وابستگی‌ها را اعمال نمی‌کند؛ مجوز فقط در `repository-read-context` دیده می‌شود.

**خروجی‌ها**
- allowlist/denylist مجوز SPDX نسخه‌دار
- ارزیاب آفلاین روی lockfile و metadata ثبت‌شده
- استثنای مالک با دلیل و انقضا؛ خروجی در Quality Gate

**معیار پذیرش**
- وابستگی با مجوز ممنوع → block با نام بسته
- مجوز نامعلوم → `unknown` و block برای ریسک بالا (نه pass)
- استثنای منقضی‌شده دوباره block می‌کند
- بدون شبکه کار می‌کند

**مرز.** مشورت حقوقی نیست؛ فهرست مجوزها را مالک تأیید می‌کند.

**ورودی لازم از مالک.** فهرست مجوزهای مجاز و ممنوع

### NX-019 — ارزیاب جامع «تعریف تمام‌شدن» محصول

| ویژگی | مقدار |
|---|---|
| موج | 3 |
| اولویت | P1 |
| اندازه | M |
| گیت تأیید | `test-runtime` |
| وابستگی | `NX-011`، `NX-014`، `NX-018`، `NX-037` |
| وضعیت | `proposed` |

**مسئله.** نتیجهٔ پذیرش، امنیت، مجوز، دسترس‌پذیری و Evidence در بخش‌های جدا می‌آیند؛ مالک باید خودش جمع کند و ممکن است ضعف یکی دیده نشود.

**خروجی‌ها**
- حکم واحد برای هر محصول/Release با اجزای نام‌دار، علت هر ضعف و پیوند Evidence
- بخش نسخه‌دار در Product Delivery Bundle
- ماتریس «جزء ناشناخته ← حکم ناقص»

**معیار پذیرش**
- حذف هر جزء از ورودی حکم را `incomplete` می‌کند، نه `pass`
- حکم با ورودی یکسان تکرارپذیر است
- آزمون پذیرش Test روی bundle نمونه

**مرز.** حکم Production ایجاد نمی‌کند؛ تأیید نهایی با مالک است.

### NX-020 — baseline بصری ساختاری برای Back Office

| ویژگی | مقدار |
|---|---|
| موج | 2 |
| اولویت | P2 |
| اندازه | M |
| گیت تأیید | `offline` |
| وابستگی | — |
| وضعیت | `proposed` |

**مسئله.** مستندات UI/UX از ابتدا «baseline visual-regression» را برنامه‌ریزی کرده‌اند و هنوز انجام نشده؛ تغییر CSS می‌تواند RTL یا تراکم صفحه‌ها را بی‌صدا بشکند.

**خروجی‌ها**
- baseline قطعی بر پایهٔ هش ساختار (جعبه‌های layout و متن)، نه تصویر دودویی، برای ۸ تا ۱۰ صفحه در سه اندازه
- داده‌ٔ fixture پایدار
- فرمان به‌روزرسانی baseline با دلیل الزامی

**معیار پذیرش**
- تغییر عمدی فاصله یا جهت در یک صفحه آزمون را fail می‌کند
- اجرای دوباره بدون تغییر PASS (بدون flake)
- در `test:browser` اجرا می‌شود

**مرز.** با `pnpm check` اصلی اجرا نمی‌شود (به مرورگر نیاز دارد)؛ روی harness موجود `tests/browser/cdp-helpers.mjs` سوار است.
