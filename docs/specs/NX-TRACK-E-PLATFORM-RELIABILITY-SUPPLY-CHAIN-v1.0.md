## هدف و جایگاه

هستهٔ Hero بزرگ شده است (server.mjs چهار و نیم هزار خط، ۲۴ migration، ۱۴۰+ سند). این مسیر بدهی ساختاری و عملیاتی را با داده‌محورکردن مسیرها، لینتر migration، آزمون خاصیتی ایزولاسیون، تأیید منشأ Release و تمرین Restore کم می‌کند.

این سند کارت ۱۰ گام این مسیر را نگه می‌دارد. نمای کلی، موج‌ها، مسیر بحرانی و مرز مجوز در [پنجاه گام جدید توسعهٔ Hero](../roadmap/NEXT-50-STEPS-20261013.md) است؛ فهرست ماشینی در `config/product-development/next-50-steps-v1.json` است و `pnpm check:next-steps` هماهنگی آن‌ها را کنترل می‌کند.

## قواعد مشترک همهٔ کارت‌ها

- وضعیت همهٔ گام‌ها `proposed` است: الزام‌آور یا مجاز به اجرا نیستند. پیش از Dispatch باید Snapshot مجوز نسخه‌دار با Step ID و نسخهٔ همین سند ثبت شود و Global Stop خاموش باشد (AGENTS.md قاعدهٔ ۱۱).
- تغییر محتوای یک کارت نسخهٔ این سند را بالا می‌برد و مجوزهای ثبت‌شده برای نسخهٔ قبلی را بی‌اثر می‌کند.
- «معیار پذیرش» شرط لازم برای `source_complete` است؛ `verified` فقط با گیت همان کارت (ستون «گیت تأیید») و Evidence واقعی ممکن است.
- هیچ کارتی مجوز Provider زنده، هزینهٔ بیرونی، تغییر Secret، Production، حذف داده یا پیام بیرونی نیست؛ این‌ها جداگانه گیت دارند (AGENTS.md قاعدهٔ ۱۲).

| ویژگی | مقدار |
|---|---|
| موج | 2 |

| اندازه | L |
| گیت تأیید | `offline` |
| وابستگی | — |
| وضعیت | `proposed` |

**مسئله.** `server.mjs` ۴٬۵۵۱ خط است و جدول مسیر برای جاروی مجوز از روی آن استخراج می‌شود؛ ثبت مسیر، کلاس مجوز، کلاس audit و شکل ورودی/خروجی در یک نقطه تعریف نشده، پس مسیر جدید می‌تواند یکی را جا بیندازد. AR-08 تقسیم فایل را می‌خواهد و این گام پایهٔ داده‌محور آن است.

**خروجی‌ها**
- مانیفست داده‌محور مسیرها (متد، مسیر، کلاس مجوز، کلاس audit، شناسهٔ schema)
- ثبت مسیرها از مانیفست
- checker: مسیر بدون کلاس مجوز/audit رد می‌شود؛ مهاجرت گروه‌به‌گروه

**معیار پذیرش**
- جاروی `wp02-route-authorization-sweep` و `read-only-route-audit` بدون تغییر رفتار پاس می‌شوند
- افزودن مسیر بدون ورودی مانیفست fail می‌کند
- گزارش، تعداد مسیرهای مهاجرت‌شده را صادقانه می‌گوید

**مرز.** بدون تغییر رفتار؛ هر گروه مسیر فقط پس از سبز بودن آزمون‌های جاروی فعلی منتقل می‌شود.

### NX-043 — لینتر ایمنی Migration

| ویژگی | مقدار |
|---|---|
| موج | 1 |
| اولویت | P1 |
| اندازه | S |
| گیت تأیید | `offline` |
| وابستگی | — |
| وضعیت | `proposed` |

**مسئله.** ۲۴ migration SQL افزایشی نوشته شده‌اند (migration 024 «سازگار با rollback» اثبات شد)، ولی این قاعده فقط رویه است؛ ابزاری از `DROP`، `RENAME`، `NOT NULL` بدون default یا حذف guard append-only جلوگیری نمی‌کند.

**خروجی‌ها**
- لینتر قطعی روی `packages/adapters/migrations/*.sql`
- قواعد: افزایشی‌بودن، idempotency، ستون جدید nullable یا دارای default، ممنوعیت حذف guard append-only
- استثنا با annotation دلیل‌دار و مالک

**معیار پذیرش**
- همهٔ ۲۴ migration فعلی PASS یا با استثنای مستند
- migration آزمایشی با `DROP COLUMN` یا حذف trigger append-only fail می‌کند
- شماره‌ها بدون شکاف و ترتیب‌دارند

**مرز.** فایل‌های migration موجود تغییر نمی‌کنند.

### NX-045 — تأیید منشأ و امضای Release پیش از Promote

| ویژگی | مقدار |
|---|---|
| موج | 4 |
| اولویت | P1 |
| اندازه | M |
| گیت تأیید | `gated-live` |
| وابستگی | `BO-OUT-003` |
| وضعیت | `proposed` |

**مسئله.** BO-OUT-003 منشأ/attestation/SBOM را به‌صورت reference ثبت می‌کند و جایگزین‌کردن آن را ناممکن می‌داند؛ اما در اسکریپت‌ها و workflowهای فعلی مرحله‌ای که attestation را واقعاً تأیید کند پیش از promote دیده نمی‌شود، فقط digest مقایسه می‌شود.

**خروجی‌ها**
- مرحلهٔ تأیید attestation با ابزار تأییدکنندهٔ قابل‌تعویض پیش از promote
- نبود attestation = block؛ ثبت نتیجه در Evidence
- Runbook

**معیار پذیرش**
- با تأییدکنندهٔ ساختگی: attestation معتبر ادامه می‌دهد، نامعتبر یا مفقود `PROVENANCE_REQUIRED`
- digest بدون attestation هرگز promote نمی‌شود
- سیاست rollback به imageهای قدیمی بدون attestation صریح و مستند است

**مرز.** تأیید واقعی به registry، کلید و ابزار بیرونی نیاز دارد و مجوز جدا می‌خواهد.

**ورودی لازم از مالک.** سیاست rollback برای imageهای قدیمی بدون attestation

| گیت تأیید | `gated-live` |

**مسئله.** ابزار `tools/audit/backup-restore.mjs` backup منطقی و restore تأییدشده را روی پایگاه disposable ثبت کرده، ولی restore روی Clean Linux واقعی هنوز blocker است، تناوبی ندارد و آنچه backup پوشش نمی‌دهد (MFA، Secret Store، بایت‌های آپلودی، نشست‌ها) فقط در متن آمده است.

**خروجی‌ها**

**معیار پذیرش**
- شبیه‌سازی محلی با PostgreSQL disposable: backup خراب → restore با کد مشخص fail؛ سالم → digestها برابر
- پایگاه موقت همیشه پاک می‌شود
- اجرای واقعی روی مقصد مالک با Evidence واقعی

**مرز.** مقصد Clean Linux و backup عملیاتی دسترسی و مجوز مالک می‌خواهد.

**مسئله.** BO-IAM-005 هنوز partial است («اجرای ProjectGrant در همهٔ لایه‌های ذخیره‌سازی»)؛ آزمون‌های فعلی نمونه‌محورند و ترکیب‌های ناخواستهٔ نقش×پروژه×مسیر را نمی‌پوشانند.

**خروجی‌ها**
- آزمون تولیدی با PRNG دارای seed (بدون وابستگی جدید) روی همهٔ مسیرهای project-scoped از جدول مسیر: چند پروژه، چند نقش، grantهای تصادفی
- ادعا: هیچ پاسخ، Audit یا جست‌وجویی داده‌ٔ پروژهٔ فاقد grant را نشان نمی‌دهد و هیچ نوشتن بین‌پروژه‌ای رخ نمی‌دهد
- چاپ seed شکست‌خورده برای بازتولید

**معیار پذیرش**
- وارد کردن عمدی یک نشت (مسیر آزمایشی بدون فیلتر پروژه) آزمون را با seed بازتولیدپذیر fail می‌کند
- تعداد ترکیب‌ها قابل‌تنظیم با سقف زمانی در `node --test`
- مسیر جدید project-scoped که در آزمون ثبت نشده باشد fail می‌کند

**مرز.** فقط آزمون؛ اصلاح هر نشت پیدا‌شده گام جدا با مجوز خودش است.

### NX-050 — بستهٔ شواهد انتشار (Release Evidence Pack)

| ویژگی | مقدار |
|---|---|
| موج | 3 |
| اولویت | P1 |
| اندازه | M |
| گیت تأیید | `test-runtime` |
| وابستگی | `NX-046`، `AR-01` |
| وضعیت | `proposed` |

**مسئله.** Evidence هر Candidate (manifest، Snapshot مجوز، نتیجهٔ check، آزمون پذیرش، شکاف‌های شناخته‌شده) در چند سند و workflow پراکنده است؛ تهیهٔ بسته برای ممیزی یا انتقال دستی است.

**خروجی‌ها**
- فرمان مالک‌محور که بستهٔ فقط‌خواندنی و بدون Secret بسازد: manifest، شناسهٔ Snapshot مجوز، خلاصهٔ `pnpm check`، نتیجهٔ acceptance، گزارش Delivery Truth، اشارهٔ rollback
- مهر digest و فرمان آفلاین verify

**معیار پذیرش**
- دستکاری هر فایل بسته verify را fail می‌کند
- بسته در حضور canary شبیه Secret ساخته نمی‌شود
- بخش مفقود (مثلاً نبود نتیجهٔ acceptance) به‌صورت `missing` ثبت می‌شود، نه حذف

**مرز.** بسته مجوزی ایجاد نمی‌کند و چیزی را منتشر نمی‌کند.
