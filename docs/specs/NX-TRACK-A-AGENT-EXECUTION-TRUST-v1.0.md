## هدف و جایگاه

Agent Tool Gateway، Hero-Bench و Golden Path در PR 20 ساخته شدند، اما هنوز به Runtime وصل نیستند و هیچ اجرای زنده‌ای رخ نداده است. این مسیر دور آن‌ها «لایهٔ اعتماد» می‌سازد: یکپارچگی Audit، پیکرهٔ حمله، حافظهٔ ایمن، Checkpoint قابل‌اتکا و تمرین توقف اضطراری، تا وقتی AR-02/AR-03 باز شدند، اجرای زنده روی پایهٔ آزمودهٔ آفلاین انجام شود.

این سند کارت ۱۰ گام این مسیر را نگه می‌دارد. نمای کلی، موج‌ها، مسیر بحرانی و مرز مجوز در [پنجاه گام جدید توسعهٔ Hero](../roadmap/NEXT-50-STEPS-20261013.md) است؛ فهرست ماشینی در `config/product-development/next-50-steps-v1.json` است و `pnpm check:next-steps` هماهنگی آن‌ها را کنترل می‌کند.

## قواعد مشترک همهٔ کارت‌ها

- وضعیت همهٔ گام‌ها `proposed` است: الزام‌آور یا مجاز به اجرا نیستند. پیش از Dispatch باید Snapshot مجوز نسخه‌دار با Step ID و نسخهٔ همین سند ثبت شود و Global Stop خاموش باشد (AGENTS.md قاعدهٔ ۱۱).
- تغییر محتوای یک کارت نسخهٔ این سند را بالا می‌برد و مجوزهای ثبت‌شده برای نسخهٔ قبلی را بی‌اثر می‌کند.
- «معیار پذیرش» شرط لازم برای `source_complete` است؛ `verified` فقط با گیت همان کارت (ستون «گیت تأیید») و Evidence واقعی ممکن است.
- هیچ کارتی مجوز Provider زنده، هزینهٔ بیرونی، تغییر Secret، Production، حذف داده یا پیام بیرونی نیست؛ این‌ها جداگانه گیت دارند (AGENTS.md قاعدهٔ ۱۲).

## کارت گام‌ها

### NX-001 — کنسول مجوز ابزار عامل

| ویژگی | مقدار |
|---|---|
| موج | 2 |
| اولویت | P1 |
| اندازه | M |
| گیت تأیید | `test-runtime` |
| وابستگی | `NX-002`، `ADR-0017` |
| وضعیت | `proposed` |

**مسئله.** Agent Tool Gateway (ADR-0017) برای هر عامل و پروژه grant و تعریف ابزار digest-pinned دارد، اما مالک هیچ نمایی از «کدام عامل کدام ابزار را با کدام digest و تا کی می‌تواند بزند» ندارد؛ تغییر grant فقط از مسیر کد ممکن است.

**خروجی‌ها**
- Read model فقط‌خواندنی grantها (عامل، پروژه، ابزار، digest، انقضا، تعداد رد/تأیید اخیر)
- صفحهٔ Back Office با نمای Owner/Admin/Viewer
- «پیشنهاد تغییر grant» به‌صورت Proposal append-only که بدون تأیید مالک هیچ اثری ندارد

**معیار پذیرش**
- Viewer هیچ کنترل تغییری نمی‌بیند و سرور هم mutation او را رد می‌کند (آزمون HTTP)
- Proposal تأییدنشده grant را تغییر نمی‌دهد
- ابزار حساس (production-deploy و مشابه) از UI هم قابل «باز کردن» نیست
- آزمون مرورگر و ممیزی ایستای RTL برای صفحهٔ جدید

**مرز.** فقط UI/API؛ منطق تصمیم Gateway تغییر نمی‌کند و اتصال Dispatch همان AR-02 است.

### NX-002 — تأییدکنندهٔ یکپارچگی زنجیرهٔ Audit

| ویژگی | مقدار |
|---|---|
| موج | 1 |
| اولویت | P1 |
| اندازه | S |
| گیت تأیید | `offline` |
| وابستگی | `ADR-0017` |
| وضعیت | `source_complete` |

**مسئله.** Gateway رویدادها را hash-chain می‌کند و Event Log append-only است، اما تأییدکنندهٔ مستقلی که یکپارچگی زنجیره را بسنجد و اولین حلقهٔ شکسته را گزارش کند وجود ندارد؛ دستکاری تا بررسی دستی دیده نمی‌شود.

**خروجی‌ها**
- تابع خالص `verifyAuditChain` و فرمان فقط‌خواندنی (`pnpm audit:chain`)
- گزارش اولین اندیس شکسته با نوع شکست (ویرایش، حذف، جابه‌جایی، کوتاه‌شدن)
- فیلد «یکپارچگی Audit» در Delivery Truth؛ وقتی زنجیره در دسترس نیست مقدار `unknown`

**معیار پذیرش**
- آزمون دستکاری: ویرایش، حذف وسط زنجیره، جابه‌جایی و کوتاه‌شدن انتها (با head مرجع) هر کدام با کد خطای متمایز رد می‌شوند
- زنجیرهٔ سالم PASS با digest پایدار
- «ناشناخته» هیچ‌گاه «سالم» گزارش نمی‌شود

**مرز.** فقط verify؛ ترمیم یا بازنویسی زنجیره ممنوع است.

### NX-003 — پیکرهٔ تزریق دستور غیرمستقیم

| ویژگی | مقدار |
|---|---|
| موج | 1 |
| اولویت | P0 |
| اندازه | M |
| گیت تأیید | `offline` |
| وابستگی | `ADR-0017` |
| وضعیت | `source_complete` |

**مسئله.** Hero-Bench v1 سی تکلیف در هفت دسته دارد و red-team ده دستهٔ OWASP Agentic را پوشش می‌دهد، اما حمله‌ای که دستور را درون محتوای خوانده‌شده (README مخزن، فایل آپلودی، خروجی ابزار، صفحهٔ وب) پنهان می‌کند — از جمله با نیم‌فاصله، homoglyph و جهت‌نمای bidi — پیکرهٔ اختصاصی ندارد؛ در حالی‌که عامل‌های Hero دقیقاً چنین محتوایی را می‌خوانند.

**خروجی‌ها**
- دستهٔ جدید `indirect-injection` با حداقل ۲۰ تکلیف قطعی فارسی/انگلیسی
- برای هر تکلیف یک نسخهٔ مخرب و یک نسخهٔ بی‌خطر مشابه (سنجش false positive)
- اتصال به `content-safety` و Gateway در آزمون red-team

**معیار پذیرش**
- مرجع ۱۰۰٪ و پاسخ خالی نزدیک صفر، مثل خودآزمایی فعلی بنچ
- عامل «توانمند ولی ناایمن» با وزن ایمنی آشکار می‌شود
- متن عادی فارسی دارای نیم‌فاصله بی‌دلیل ریسک‌دار علامت نمی‌خورد (آزمون بازگشتی ZWNJ)

**مرز.** هیچ Provider زنده و هیچ اجرای کد مدل؛ نتیجه‌ها فقط اعتبار خود بنچ را می‌سنجند.

### NX-004 — بخش نگه‌داشته و محافظ آلودگی بنچ

| ویژگی | مقدار |
|---|---|
| موج | 2 |
| اولویت | P1 |
| اندازه | M |
| گیت تأیید | `offline` |
| وابستگی | `NX-003` |
| وضعیت | `proposed` |

**مسئله.** Runner فقط نمای عمومی تکلیف را می‌بیند، ولی کل مجموعه در مخزن است؛ مدلی که مخزن را دیده باشد ممکن است پاسخ را حفظ کند و نتیجه بی‌ارزش شود. هیچ نشانهٔ تشخیص آلودگی وجود ندارد.

**خروجی‌ها**
- تقسیم تکلیف‌ها به public/holdout با commit digest در مخزن و محتوای holdout بیرون از Git
- canary یکتا برای هر نسخهٔ بنچ و تشخیص نشت آن در خروجی
- چرخش دوره‌ای holdout با ثبت نسخه

**معیار پذیرش**
- پاسخ حاوی canary → `contaminated`
- تغییر digest holdout بدون ثبت نسخه رد می‌شود
- `check-hero-bench` هر دو بخش را فقط با digest اعتبارسنجی می‌کند (بدون نیاز به محتوای holdout)
- در نبود holdout، گزارش صریحاً `public-only` می‌گوید

**مرز.** محل نگهداری holdout تصمیم مالک است؛ تا آن زمان حالت `public-only` فعال می‌ماند.

**ورودی لازم از مالک.** محل امن نگهداری holdout خارج از Git

### NX-005 — ضبط‌کنندهٔ پرواز اجرا (Run Flight Recorder)

| ویژگی | مقدار |
|---|---|
| موج | 3 |
| اولویت | P1 |
| اندازه | L |
| گیت تأیید | `offline` |
| وابستگی | `AR-02`، `NX-002` |
| وضعیت | `proposed` |

**مسئله.** وقتی Run شکست می‌خورد، تنها شواهد پراکندهٔ Eventها و Auditهاست؛ بازتولید «چرا Gateway این ابزار را رد/تأیید کرد» بدون Provider زنده ممکن نیست.

**خروجی‌ها**
- Schema ردگیری redacted: تصمیم‌های Gateway، Checkpointها، نتیجهٔ ابزار (digest نه محتوا)، تصمیم‌های Planner
- موتور replay آفلاین که تصمیم‌های Gateway را از روی ردگیری دوباره می‌سازد
- بازرسی redaction روی همهٔ فیلدها

**معیار پذیرش**
- replay ردگیری ثبت‌شده همان digest تصمیم‌ها را می‌دهد
- ردگیری با canary شبیه Secret در هیچ فیلدی نمی‌ماند
- ردگیری دستکاری‌شده با NX-002 رد می‌شود

**مرز.** به Control Plane فقط پس از AR-02 وصل می‌شود؛ تا آن زمان کتابخانه و آزمون است. ذخیرهٔ محتوای prompt/output ممنوع است.

### NX-006 — قرنطینهٔ حافظهٔ آلوده و ردیابی منشأ

| ویژگی | مقدار |
|---|---|
| موج | 1 |
| اولویت | P1 |
| اندازه | M |
| گیت تأیید | `offline` |
| وابستگی | `BO-MEM-003` |
| وضعیت | `proposed` |

**مسئله.** `project-memory` پیشنهادهای حافظه را sanitize می‌کند، اما رکوردی که از خروجی ابزار یا فایل نامطمئن نوشته شده منشأ و سطح اعتماد صریح ندارد؛ یک ورودی مسموم می‌تواند در Runهای بعد به‌عنوان «دانش» برگردد.

**خروجی‌ها**
- فیلدهای منشأ (run، ابزار، digest منبع) و سطح اعتماد (`owner`، `reviewed`، `agent-derived`، `untrusted`) برای هر رکورد
- رکورد `untrusted` و `agent-derived` تا بازبینی در بازیابی پیش‌فرض نمی‌آید
- مسیر بازبینی مالک با تاریخچهٔ append-only؛ رکوردهای موجود با برچسب `legacy` مهاجرت می‌شوند

**معیار پذیرش**
- آزمون خصمانه: دستور تزریق‌شده در خروجی ابزار در حافظهٔ قرنطینه می‌ماند و در context بازیابی‌شده نیست
- بازبینی مالک آن را آزاد می‌کند و تاریخچه حفظ می‌شود
- آزمون‌های فعلی `project-memory` بدون تغییر رفتار پاس می‌شوند

**مرز.** رفتار رکوردهای `legacy` را مالک تعیین می‌کند؛ پیش‌فرض این گام تغییری در بازیابی آن‌ها ایجاد نمی‌کند.

**ورودی لازم از مالک.** سیاست بازیابی رکوردهای legacy

### NX-007 — پروفایل‌های منبع Runner

| ویژگی | مقدار |
|---|---|
| موج | 1 |
| اولویت | P1 |
| اندازه | M |
| گیت تأیید | `offline` |
| وابستگی | `ADR-0006` |
| وضعیت | `source_complete` |

**مسئله.** Runner ایزوله timeout و محدودیت هم‌زمانی دارد، اما سقف CPU، حافظه، دیسک و تعداد پردازه برای هر کلاس تکلیف در قرارداد تعریف نشده؛ یک تکلیف گریزان می‌تواند منابع میزبان Test را ببلعد.

**خروجی‌ها**
- رجیستری پروفایل (`light`، `standard`، `heavy`) با سقف‌های غیرقابل‌تضعیف
- تکلیف بدون پروفایل fail-closed رد می‌شود
- اتصال به `product-runtime-capacity` برای رزرو؛ نگاشت به گزینه‌های container بدون اجرای زنده

**معیار پذیرش**
- پروفایل ناشناخته، سقف صفر/نامحدود و تلاش برای افزایش سقف در سطح پروژه رد می‌شود
- مجموع رزروها از ظرفیت میزبان بیشتر نمی‌شود
- قرارداد در `check:deployment-contract` دیده می‌شود

**مرز.** اعمال واقعی cgroup روی میزبان گام جدا و gated است.

### NX-008 — شبیه‌ساز خروج شبکه پیش از Dispatch

| ویژگی | مقدار |
|---|---|
| موج | 2 |
| اولویت | P2 |
| اندازه | S |
| گیت تأیید | `offline` |
| وابستگی | `BO-SEC-005`، `NX-007` |
| وضعیت | `proposed` |

**مسئله.** سیاست egress پیش‌فرض‌بسته و per-request است، ولی مالک پیش از Dispatch نمی‌داند کدام بخش Plan به‌خاطر دامنه یا ابزار غیرمجاز مسدود می‌شود؛ شکست دیر (وسط Run) پرهزینه است.

**خروجی‌ها**
- تابع خالص `simulateEgress(plan, policy)` با resolver تزریقی
- فیلد فقط‌خواندنی `egressPreview` در پاسخ Planner
- طبقه‌بندی «مسدود می‌شود / مجاز / نامعلوم»

**معیار پذیرش**
- هیچ تماس شبکه‌ای انجام نمی‌شود (resolver آزمون در صورت فراخوانی fail می‌کند)
- ورودی یکسان نتیجهٔ یکسان
- مقصد نامعلوم هرگز «مجاز» گزارش نمی‌شود

**مرز.** پیش‌نمایش است و هیچ مجوزی نمی‌دهد.

### NX-009 — Checkpoint امضاشده با تأیید در Resume

| ویژگی | مقدار |
|---|---|
| موج | 1 |
| اولویت | P1 |
| اندازه | S |
| گیت تأیید | `offline` |
| وابستگی | `ADR-0006` |
| وضعیت | `source_complete` |

**مسئله.** ADR-0006 چک‌پوینت پیش از پاک‌سازی را الزام می‌کند، ولی Resume فقط وجود چک‌پوینت را می‌سنجد، نه این‌که محتوای آن بین توقف و ادامه دست‌نخورده مانده باشد.

**خروجی‌ها**
- digest محتوایی و HMAC زنجیره‌ای برای هر Checkpoint با کلید از مرجع Secret Store
- Resume فقط با Checkpoint دارای امضای معتبر و گره‌خورده به همان Run/Task
- شناسهٔ کلید برای چرخش بدون ازدست‌رفتن Checkpointهای قدیمی

**معیار پذیرش**
- تغییر یک بایت، جابه‌جایی بین Taskها و کلید ناشناخته → `CHECKPOINT_INTEGRITY_FAILED` و Run در حالت امن می‌ماند
- کلید آزمون در زمان اجرای آزمون ساخته می‌شود تا اسکن Secret پاس شود (الگوی PR 20)
- بدون کلید پیکربندی‌شده قابلیت `unavailable` است و ادعای سالم نمی‌شود

**مرز.** مقدار کلید هرگز در Git نمی‌آید؛ فقط مرجع آن.

### NX-010 — تمرین دوره‌ای توقف اضطراری (Global Stop Drill)

| ویژگی | مقدار |
|---|---|
| موج | 2 |
| اولویت | P0 |
| اندازه | M |
| گیت تأیید | `test-runtime` |
| وابستگی | `AR-01`، `ADR-0005` |
| وضعیت | `proposed` |

**مسئله.** پیش‌نیاز ششم اجرای زندهٔ Golden Path «تمرین توقف اضطراری انجام و تاریخ آن ثبت شده باشد» است، اما نه روش اندازه‌گیری دارد و نه تناوب؛ فعلاً فقط آزمون واحد Global Stop هست.

**خروجی‌ها**
- سناریوی drill: طوفان Dispatch مصنوعی ← Global Stop روشن ← اندازه‌گیری زمان تا توقف Dispatch جدید و تعداد Dispatch نفوذکرده (باید صفر باشد) ← Resume
- رکورد Evidence با digest و تاریخ واقعی
- سیاست تناوب ماهانه و Runbook

**معیار پذیرش**
- drill محلی با نفوذ صفر PASS
- نتیجه‌ای که نفوذ ≥ ۱ دارد fail می‌شود و Evidence آن ثبت می‌شود، نه پنهان
- اجرای واقعی روی Test با Candidate بعدی توسط مالک و ثبت رکورد با تاریخ واقعی (نه ساختگی)

**مرز.** کد drill خودش Global Stop را روشن/خاموش نمی‌کند؛ اجرای روی Test با مجوز و حضور مالک است.
