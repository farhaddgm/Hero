# HERO-021 v1.0 — پایلوت انتهابه‌انتها

وضعیت: پیش‌نویس طراحی. این سند فقط پروتکل پایلوت و معیارهای پذیرش آن را مشخص می‌کند. هیچ اجرای واقعی Provider، ساخت اپلیکیشن برای کاربر، هزینهٔ خارجی، استقرار، تغییر Secret یا عملیات غیرقابل‌بازگشت در این گام انجام نمی‌شود.

## هدف

Hero باید بتواند یک درخواست کوتاه و فارسیِ کاربر را به یک مسیر قابل‌فهم، قابل‌کنترل و قابل‌ممیزی برای ساخت یک اپلیکیشن وب یا موبایل تبدیل کند. کاربر باید بتواند بین دو رفتار انتخاب کند:

- «در هر گیت با من چک کن»؛ Hero در گیت‌های تعریف‌شده متوقف می‌شود و تصمیم روشن می‌خواهد.
- «تا تحویل ادامه بده»؛ Hero فقط در محدودهٔ مجوز فعال، تا یک checkpoint ایمن ادامه می‌دهد و هر اقدام حساس را همچنان جداگانه متوقف می‌کند.

خروجی پایلوت قرار نیست ادعای تحویل محصول نهایی کند. خروجیِ معتبر، شواهدی است که نشان دهد مسیر درخواست تا برنامه، توسعه، بازبینی و ارزیابی کیفیت به‌درستی و fail-closed مدل شده است.

## دامنه و مرزها

1. ورودی پایلوت یک درخواست متنی فارسی، انتخاب پلتفرم (`web`، `mobile` یا `both`) و حالت اختیار است.
2. خروجی مورد انتظار شامل برنامهٔ قابل‌تأیید، گراف وظایف، وضعیت گیت‌ها، بستهٔ handoff برای Cursor، گزارش بازبینی Claude و خلاصهٔ کیفیت است.
3. Codex/ChatGPT نقش Planner و Lead Developer، Claude نقش Reviewer خصمانه و Cursor نقش محیط Human-in-the-loop را دارد.
4. نبود CLI، دسترسی یا اعتبار Provider نباید با حدس، mock پنهان یا فراخوانی خارجی جبران شود؛ Hero باید وضعیت `blocked` با علت مشخص ثبت کند.
5. استفادهٔ واقعی از Provider، ارسال پیام بیرونی، پرداخت، deploy، merge، تولید/تغییر Secret، حذف داده و هر عمل غیرقابل‌بازگشت خارج از دامنهٔ این سند است و مجوز مستقل می‌خواهد.

## تجربهٔ کاربر ساده

1. کاربر یک جملهٔ ساده می‌نویسد؛ مانند «برای فروشگاه من صفحهٔ سفارش بساز».
2. Hero درخواست را به زبان ساده بازگو می‌کند، فرض‌ها و ابهام‌های حیاتی را جدا می‌سازد و یک برنامهٔ قابل‌بررسی تولید می‌کند.
3. Hero وابستگی‌ها، ریسک‌ها، معیار پذیرش و هزینه/عملیات حساس را پیش از dispatch نمایش می‌دهد.
4. پس از مجوز مؤثر، Hero کارها را به بسته‌های مستقل با مرز فایل و worktree جدا تبدیل می‌کند.
5. Hero شواهد توسعه، تست و review را به یک گزارش تحویل قابل‌فهم برای کاربر متصل می‌کند؛ Cursor محل مشاهده و اصلاح انسانی باقی می‌ماند.

اگر درخواست فاقد اطلاعات حیاتی باشد، Hero فقط همان ابهام حیاتی را سؤال می‌کند. در غیر این صورت، فرض‌های قابل‌بازگشت را در برنامه ثبت و ادامه می‌دهد.

## پروتکل پایلوت

### 1. دریافت و تحلیل

- یک `Pilot Request` نسخه‌دار با شناسهٔ یکتا ساخته می‌شود؛ متن خام درخواست، پلتفرم هدف، حالت اختیار و فرض‌های ثبت‌شده را نگه می‌دارد.
- Planner یک `Feature Brief` و `Task Graph` می‌سازد: هدف، خارج از دامنه، معیار پذیرش، وابستگی‌ها، ریسک‌ها و مرز هر وظیفه.
- پیش از هر dispatch، Step ID و نسخهٔ سند با authorization snapshot تطبیق داده می‌شود و Global Stop باید خاموش باشد.

### 2. طراحی و تقسیم کار

- هر وظیفه فقط یک مالک اصلی دارد و هم‌زمان با وظیفه‌ای که فایل یا منبع مشترک دارد اجرا نمی‌شود.
- مرزهای توسعه با worktree و branch مستقل تعیین می‌شوند؛ دسترسی به پروژه‌های هم‌جوار یا parent path ممنوع است.
- Router باید دلیل انتخاب نقش را ثبت کند؛ انتخاب Provider یک ادعای کیفیت یا تضمین دسترسی نیست.

### 3. توسعه و بازبینی

- بستهٔ Codex/ChatGPT شامل feature brief، قراردادهای مصوب، معیار پذیرش و محدودهٔ فایل است.
- بستهٔ Claude شامل diff یا artifact قابل‌بررسی، focus review (امنیت، edge case، سازگاری معماری، تست) و قالب یافته‌های ساخت‌یافته است.
- بستهٔ Cursor شامل خلاصهٔ تغییرات، دستور اجرای محلی، نتایج تست و مواردی است که فقط انسان باید ببیند یا تصمیم بگیرد.
- اگر یک provider در دسترس نباشد، orchestrator نباید جای آن تأیید جعلی ثبت کند؛ وضعیت باید `blocked: provider unavailable` باشد.

### 4. کیفیت و تحویل

- قبل از هر پیشرفت، قراردادهای حاکمیت، مجوز، Global Stop، clean-room، و معیار پذیرش بررسی می‌شوند.
- تست‌ها باید نتیجهٔ واقعی، command، exit code، artifact و زمان ثبت‌شده داشته باشند؛ «موفق فرض شد» معتبر نیست.
- گزارش نهایی باید وضعیت هر وظیفه، یافته‌های بازبینی، نتیجهٔ تست، محدودیت‌های باقی‌مانده و مسیر بازگشت را جدا نشان دهد.
- موفقیت پایلوت فقط با همهٔ گیت‌های لازم و شواهد واقعی اعلام می‌شود. هر گیت نامعتبر یا ناقص، کل مسیر را fail-closed متوقف می‌کند.

## مدل اختیار و توقف

| وضعیت | رفتار Hero |
| --- | --- |
| تأیید موردی | قبل از هر گیت توسعهٔ بعدی، منتظر تصمیم کاربر می‌ماند. |
| اختیار کاملِ snapshot | فقط گام‌ها و نسخه‌های مشخص در snapshot فعال را تا checkpoint ایمن ادامه می‌دهد. |
| Global Stop | dispatch جدید را فوراً متوقف می‌کند و اجرای جاری در نزدیک‌ترین checkpoint ایمن pause می‌شود. |
| مجوز حساسِ جداگانه | برای deploy، هزینه، Secret، پیام بیرونی، حذف/تغییر غیرقابل‌بازگشت و production توقف اجباری است. |

اختیار کامل هرگز مجوز دائمی یا مجوز اجرای عملیاتی حساس نیست. تغییر نسخهٔ سند، مجوز قبلی را برای نسخهٔ جدید معتبر نمی‌گذارد.

## قرارداد شواهد

برای هر پایلوت، این artifactها باید وجود داشته باشند:

- `pilot-request`، `feature-brief` و `task-graph` نسخه‌دار
- تصمیم router و دلیل انتخاب نقش
- authorization id، Step ID، نسخهٔ سند و نتیجهٔ Global Stop check
- شناسهٔ worktree/branch بدون path میزبان یا اشاره به پروژهٔ دیگر
- نتیجهٔ واقعی تست و review با timestamps ثابت و append-only
- گزارش handoff برای Cursor و گزارش تحویل قابل‌فهم برای کاربر

هیچ artifact نباید Secret، token، password، مسیر مطلق میزبان یا دادهٔ پروژهٔ دیگر را در خود نگه دارد.

## معیار پذیرش طراحی

- جریان کامل از درخواست فارسی تا گزارش تحویل، state و contractهای لازم را بدون وابستگی پنهان تعریف کند.
- سه نقش Codex/ChatGPT، Claude و Cursor مسئولیت‌های مکمل و مرز handoff روشن داشته باشند.
- راه اجرای موردی، اختیار snapshot و Global Stop دقیق و fail-closed باشد.
- نبود زیرساخت یا Provider به وضعیت مسدودِ قابل‌فهم منتهی شود، نه شبیه‌سازیِ یک اجرای واقعی.
- استقلال مخزن، worktree، تست و شواهد با قواعد بنیادین Hero سازگار باشد.

## گیت اجرای واقعی بعدی

اجرای واقعی پایلوت تا وقتی همهٔ شروط زیر با شواهد واقعی برقرار نشده‌اند، ممنوع است:

1. HERO-020 باید روی محیط Linux پاک با Docker/Compose و restore قابل‌اثبات تکمیل شود.
2. محیط اجرای Linux و Docker باید آماده و جدا از هر پروژهٔ دیگر باشد.
3. دسترسی واقعی هر Provider باید با مجوز و روش احراز هویت جداگانه و بدون ثبت Secret در repository یا Google Sheet فراهم شود.
4. خود درخواست پایلوت، پلتفرم هدف و معیار پذیرش آن باید مشخص باشد.
5. هر هزینه، پیام بیرونی، deploy یا عملیات حساس باید مجوز مستقل همان عملیات را داشته باشد.

تا پیش از این گیت، تکمیل این سند فقط «آمادگی طراحی» محسوب می‌شود و نباید در رودمپ به‌عنوان اجرای موفق پایلوت ثبت شود.
