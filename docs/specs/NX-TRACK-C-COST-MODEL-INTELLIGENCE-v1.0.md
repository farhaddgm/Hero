## هدف و جایگاه

اجرای زنده بدون کنترل هزینه و بدون شناخت مدل‌ها ممکن نیست. این مسیر قیمت‌ها را fail-closed می‌کند، برآورد را با واقعیت کالیبره می‌کند، مسیردهی و Failover را امن و قابل‌شبیه‌سازی می‌کند و مجوز هزینه را برای مالک ساده می‌سازد؛ بدون این‌که خودش مجوزی صادر کند.

این سند کارت ۱۰ گام این مسیر را نگه می‌دارد. نمای کلی، موج‌ها، مسیر بحرانی و مرز مجوز در [پنجاه گام جدید توسعهٔ Hero](../roadmap/NEXT-50-STEPS-20261013.md) است؛ فهرست ماشینی در `config/product-development/next-50-steps-v1.json` است و `pnpm check:next-steps` هماهنگی آن‌ها را کنترل می‌کند.

## قواعد مشترک همهٔ کارت‌ها

- وضعیت همهٔ گام‌ها `proposed` است: الزام‌آور یا مجاز به اجرا نیستند. پیش از Dispatch باید Snapshot مجوز نسخه‌دار با Step ID و نسخهٔ همین سند ثبت شود و Global Stop خاموش باشد (AGENTS.md قاعدهٔ ۱۱).
- تغییر محتوای یک کارت نسخهٔ این سند را بالا می‌برد و مجوزهای ثبت‌شده برای نسخهٔ قبلی را بی‌اثر می‌کند.
- «معیار پذیرش» شرط لازم برای `source_complete` است؛ `verified` فقط با گیت همان کارت (ستون «گیت تأیید») و Evidence واقعی ممکن است.
- هیچ کارتی مجوز Provider زنده، هزینهٔ بیرونی، تغییر Secret، Production، حذف داده یا پیام بیرونی نیست؛ این‌ها جداگانه گیت دارند (AGENTS.md قاعدهٔ ۱۲).

## کارت گام‌ها

### NX-021 — گیت تازگی قیمت‌ها (Price Freshness)

| ویژگی | مقدار |
|---|---|
| موج | 1 |
| اولویت | P0 |
| اندازه | S |
| گیت تأیید | `offline` |
| وابستگی | — |
| وضعیت | `proposed` |

**مسئله.** `estimateRun` برای قیمت منقضی فقط «هشدار» می‌دهد و catalog فقط هنگام normalize اعتبار `validUntil` را می‌سنجد؛ مقایسهٔ سقف هزینه با برآورد کهنه می‌تواند سقف ناکافی را «کافی» نشان دهد.

**خروجی‌ها**
- سیاست fail-closed: قیمت منقضی یا بدون `validUntil` برای مقایسهٔ سقف/برآورد «غیرقابل‌اتکا» است
- گزارش diff بین نسخه‌های catalog (افزایش، کاهش، حذف مدل)
- هشدار «N روز تا انقضا»

**معیار پذیرش**
- مقایسهٔ سقف مجوز با برآورد بر پایهٔ قیمت منقضی `PRICE_STALE` برمی‌گرداند و `golden.readiness()` آن را شرط ناقص می‌داند
- diff قطعی است
- رفتار هشداری فعلی برای نمایش صرف حفظ می‌شود

**مرز.** به‌روزرسانی قیمت از منبع بیرونی گام جدا و gated است؛ عدد قیمت را عامل نمی‌سازد.

**خروجی‌ها**

- زیر حداقل نمونه (۳) مقدار `insufficient-data` است نه عدد
- نمایش فقط برای Owner/Admin و read-audited

**مرز.** سقف هزینه را خودکار تغییر نمی‌دهد.

### NX-023 — پیش‌بینی نرخ مصرف و تاریخ اتمام بودجه

| ویژگی | مقدار |
|---|---|
| موج | 2 |
| اولویت | P2 |
| اندازه | S |
| گیت تأیید | `test-runtime` |
| وابستگی | `NX-021` |
| وضعیت | `proposed` |

**مسئله.** سقف نرم/سخت پروژه و pause امن وجود دارد، ولی مالک تا لحظهٔ رسیدن به آستانه نمی‌داند با نرخ فعلی بودجه کی تمام می‌شود.

**خروجی‌ها**
- نرخ مصرف پنجره‌ای
- تاریخ پیش‌بینی‌شدهٔ رسیدن به سقف نرم/سخت با بازهٔ عدم‌قطعیت
- آیتم Inbox داخلی برای هشدار زودهنگام (بدون پیام بیرونی)

**معیار پذیرش**
- با داده‌ٔ مصنوعی با نرخ ثابت پیش‌بینی درست است
- داده‌ٔ ناکافی `unknown` است
- Inbox آیتم تکراری نمی‌سازد (dedup موجود)
- هیچ اعلان بیرونی ارسال نمی‌شود

**مرز.** اعمال سقف همان سازوکار موجود است؛ این گام فقط پیش‌بینی می‌کند.

|---|---|
| موج | 3 |
| اولویت | P2 |
| اندازه | M |
| گیت تأیید | `offline` |
| وابستگی | `NX-021`، `NX-025`، `NX-030` |
| وضعیت | `proposed` |

**مسئله.** تغییر Binding نقش←مدل امروز بدون پیش‌بینی اثر هزینه و کیفیت انجام می‌شود.

**خروجی‌ها**
- بازپخش پروفایل مصرف تاریخی/مصنوعی با Bindingهای جایگزین
- برآورد هزینه با catalog تازه (NX-021) و کیفیت با امتیاز Hero-Bench یا ماتریس قابلیت
- خروجی فقط Proposal مقایسه‌ای

**معیار پذیرش**
- خروجی قطعی
- مدل بدون امتیاز بنچ «کیفیت نامعلوم» است، نه برابر مدل فعلی
- هیچ Bindingی تغییر نمی‌کند (آزمون)

**مرز.** داده‌ٔ کیفیت زنده به AR-04 نیاز دارد؛ تا آن زمان فقط داده‌ٔ مصنوعی و ماتریس قابلیت.

### NX-025 — تخصیص‌دهندهٔ بودجهٔ توکن برای context

| ویژگی | مقدار |
|---|---|
| موج | 1 |
| اولویت | P1 |
| اندازه | M |
| گیت تأیید | `offline` |
| وابستگی | — |
| وضعیت | `proposed` |

**مسئله.** `assembleContext` در `ai-orchestration.mjs` از Project Memory فقط با سقف تعداد آیتم (`maxItems`، پیش‌فرض ۱۲) می‌خواند؛ سقف مبتنی بر توکن، اولویت‌بندی منابع و گزارش «چه چیزی حذف شد» دیده نمی‌شود، پس با رشد حافظه حذف خاموش ارجاع‌ها ممکن است.

**خروجی‌ها**
- سیاست تخصیص بودجهٔ توکن به‌ازای نقش مقصد (سقف، کف برای Citation، اولویت منابع)
- تخمین توکن قطعی و آفلاین با برچسب `estimate` (بدون tokenizer بیرونی)
- گزارش `omitted` با دلیل در خروجی context

**معیار پذیرش**
- با حافظهٔ بزرگ مصنوعی خروجی از سقف نمی‌گذرد و `omitted` همهٔ حذف‌شده‌ها را با دلیل می‌دهد
- آیتم دارای Citation الزامی پیش از آیتم بدون آن حذف نمی‌شود
- ورودی یکسان خروجی یکسان
- آزمون‌های `project-memory` و `ai-orchestration` بدون تغییر و فیلتر نقش/ایزولاسیون دست‌نخورده

**مرز.** ایزولاسیون پروژه/نقش را تغییر نمی‌دهد؛ فقط انتخاب و گزارش را دقیق می‌کند.

### NX-026 — سیاست Failover امن Provider

| ویژگی | مقدار |
|---|---|
| موج | 2 |
| اولویت | P1 |
| اندازه | M |
| گیت تأیید | `offline` |
| وابستگی | `NX-030` |
| وضعیت | `proposed` |

**مسئله.** در کد فعلی `fallback` فقط پیام خطای امن است؛ سیاست صریحی برای «اگر Provider الف شکست خورد، به کدام مدل و با چه شرط‌هایی سقوط کن» وجود ندارد و سقوط بی‌قاعده می‌تواند به مدلی با ایمنی، حریم داده یا هزینهٔ متفاوت برسد.

**خروجی‌ها**
- قرارداد زنجیرهٔ failover به‌ازای کلاس تکلیف
- ارزیاب: فقط مدل‌های allow-list با رده ایمنی برابر یا بالاتر، بررسی مجدد سقف هزینه در هر پرش، ممنوعیت پرش به Provider بدون مجوز هزینه
- ثبت دلیل پرش در Audit

**معیار پذیرش**
- پرش به مدل خارج allow-list، به رده پایین‌تر برای تکلیف حساس یا بدون مجوز هزینه رد می‌شود
- پرش مجاز دلیل و هزینه را ثبت می‌کند
- رفتار timeout/retry/circuit breaker موجود بدون تغییر

**مرز.** اجرای زنده نمی‌شود؛ فقط قرارداد و ارزیاب.

### NX-027 — سازندهٔ پیش‌نویس مجوز هزینه

| ویژگی | مقدار |
|---|---|
| موج | 2 |
| اولویت | P0 |
| اندازه | M |
| گیت تأیید | `offline` |
| وابستگی | `NX-021` |
| وضعیت | `proposed` |

**مسئله.** اجرای زندهٔ Golden Path و Hero-Bench (AR-03، AR-04) به مجوز هزینهٔ بیرونی نسخه‌دار نیاز دارد؛ ساخت دستی این Snapshot JSON با سقف مناسب (≥ بدترین برآورد) خطاپذیر و برای مالک غیرمستقیم است.

**خروجی‌ها**
- ابزار تولید پیش‌نویس Snapshot از ورودی ساده (Provider، مدل‌های مجاز، سقف، انقضا، Step ID)
- نمایش فارسی بدترین هزینه با `estimateRun`
- اعتبارسنجی ساختار با همان verifier؛ خروجی فایل پیش‌نویس برای commit مالک

**معیار پذیرش**
- پیش‌نویس با سقف کمتر از بدترین برآورد، قیمت منقضی یا Step ID/نسخهٔ سند ناهمخوان ساخته نمی‌شود
- ابزار هرگز Snapshot را «فعال» نمی‌کند
- فایل خروجی هیچ Secret ندارد

**مرز.** مجوز نمی‌دهد؛ صدور و ثبت مجوز فقط با مالک است (قواعد ۸ و ۱۱ در AGENTS.md).

|---|---|

| اولویت | P2 |

| گیت تأیید | `test-runtime` |
| وابستگی | `NX-030`، `BO-AI-002` |
| وضعیت | `proposed` |

**مسئله.** BO-AI-002 می‌گوید سلامت و توصیه هست ولی گردش‌کار مالک‌تأییدشدهٔ جایگزینی مدل نیست؛ مدل منسوخ‌شده می‌تواند ناگهان در یک Binding بشکند.

**خروجی‌ها**
- تاریخ deprecation و جایگزین پیشنهادی در رجیستری مدل
- هشدار N روز پیش از سقوط
- Proposal جایگزینی با شبیه‌سازی اثر و تأیید مالک؛ تاریخچهٔ append-only

**معیار پذیرش**
- Binding روی مدل منقضی‌شده در Planner `blocked` است، نه fallback خاموش
- Proposal بدون تأیید اثری ندارد
- نسخهٔ Binding قبلی برای rollback می‌ماند

**مرز.** جایگزینی خودکار ممنوع است.

**ورودی لازم از مالک.** allow-list رسمی مدل‌ها

### NX-030 — ماتریس قابلیت مدل‌ها

| ویژگی | مقدار |
|---|---|
| موج | 1 |
| اولویت | P2 |
| اندازه | S |
| گیت تأیید | `offline` |
| وابستگی | — |
| وضعیت | `proposed` |

**مسئله.** ویژگی‌های مدل‌ها (پنجرهٔ context، tool use، خروجی ساخت‌یافته، اقامت داده) میان تنظیمات و قیمت‌ها پراکنده است؛ Planner و قالب‌ها ماتریس واحدی برای تطبیق ندارند.

**خروجی‌ها**
- رجیستری نسخه‌دار قابلیت به‌ازای (Provider، مدل) با مقدار `unknown` صریح و تاریخ راستی‌آزمایی
- API خواندنی
- تابع تطبیق «این تکلیف چه قابلیتی لازم دارد»

**معیار پذیرش**
- قابلیت نامعلوم هرگز «پشتیبانی می‌شود» نمی‌شود
- ورودی بدون تاریخ راستی‌آزمایی یا کهنه علامت می‌خورد
- Planner فقط یک فیلد مشورتی دریافت می‌کند و تصمیم تغییر نمی‌کند

**مرز.** مقدارها از مستندات رسمی هر Provider توسط انسان راستی‌آزمایی می‌شوند؛ عامل آن‌ها را حدس نمی‌زند.
