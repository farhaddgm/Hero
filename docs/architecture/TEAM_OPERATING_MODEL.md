# مدل عملیاتی تیم‌های Hero

## هدف

Hero فقط یک زنجیرهٔ Provider نیست؛ یک شرکت نرم‌افزاری شبیه‌سازی‌شده است که در آن هر تیم یک واحد عملیاتی مستقل، نسخه‌دار و قابل حسابرسی است. تیم از یک نام ساده فراتر می‌رود و این قرارداد را دارد:

```text
Team = مسئولیت + اختیار + ورودی + خروجی + اصول + همکاران + سطح خودکارسازی
```

اصول سطح شرکت در `docs/architecture/CRITICAL_PRINCIPLES.md` از قرارداد تیم جدا هستند و به‌صورت inherited روی همهٔ تیم‌ها و محصولات اعمال می‌شوند. اصل تیمی می‌تواند جزئیات نقش را مشخص کند، اما نمی‌تواند اصل حیاتی Hero را تضعیف یا حذف کند.

کاتالوگ مرحلهٔ اول دقیقاً از شیت عملیاتی مالک پروژه گرفته شده و شامل ۱۱ تیم است. تعریف ماشینی آن در `packages/contracts/src/team.mjs` و کنترل deterministic آن در `packages/domain/src/team-registry.mjs` قرار دارد.

## تیم‌های مرحلهٔ اول

| تیم | مسئولیت اصلی | خروجی مرجع |
| --- | --- | --- |
| راهبرو | ارکستراسیون و مدیریت تحویل | راه‌حل نهایی، وضعیت، ریسک و بستهٔ تحویل |
| ایده‌پردازو | کشف فرصت و تولید گزینه‌های خلاقانه | ایده‌ها، سناریوها و فرضیه‌های قابل‌آزمون |
| تحلیلگرو | تحلیل مسئله، بازار، کسب‌وکار و تصمیم | پروندهٔ تحلیل، شواهد و توصیهٔ تصمیم |
| محصولو | تبدیل مسئله به محصول قابل ساخت | PRD، MVP، نیازمندی، معیار پذیرش و بک‌لاگ |
| دیزاینرو | طراحی تجربه و رابط کاربری | معماری اطلاعات، وایرفریم، UI و پروتوتایپ |
| معمارو | معماری نرم‌افزار و استاندارد فنی | طرح معماری، ADR، قرارداد API و استاندارد Repository |
| دولوپرو | پیاده‌سازی نرم‌افزار | کد، تست، مستندات اجرا و Artifact فنی |
| تسترو | راستی‌آزمایی کیفیت و رفتار سیستم | برنامهٔ تست، نتیجه، باگ و وضعیت پذیرش |
| امینتو | امنیت محصول، کد و فرایند | مدل تهدید، گزارش امنیت و وضعیت ریسک |
| عملیاتو | زیرساخت، استقرار و پایداری | سرویس، Runbook، گزارش عملیات و شواهد بازیابی |
| داده‌و | داده، سنجه‌ها و هوش مصنوعی | مدل داده، KPI، داشبورد و بینش داده‌محور |

## قرارداد کاری تیم

هر تیم با یک `teamId` پایدار، نسخهٔ قرارداد، وضعیت، سابقهٔ بررسی، وضعیت آموزش، تخصیص‌های پروژه و سیاست خودکارسازی شناخته می‌شود.

### ورودی

ورودی تیم فقط متن خام نیست. بستهٔ ورودی باید شامل مسئله یا Artifact قبلی، نسخهٔ قرارداد، معیار پذیرش، محدودیت، ریسک و سطح اختیار باشد. ورودی بدون نسخه یا خارج از پروژهٔ جاری قابل استفاده نیست.

### خروجی

خروجی تیم باید یک Artifact قابل اشاره، نسخه‌دار و قابل بررسی باشد و حداقل این موارد را روشن کند:

- چه تصمیم یا تغییری تولید شده است؛
- به کدام ورودی، نیازمندی و معیار پذیرش متصل است؛
- چه تست، شواهد یا بازبینی انجام شده است؛
- چه ریسک، فرض یا ابهامی باقی مانده است؛
- تیم بعدی دقیقاً چه چیزی را دریافت می‌کند.

### اصول

اصول هر تیم در قرارداد ثبت می‌شود و مالک پروژه می‌تواند آن را برای هر تیم جداگانه تأیید، رد یا برای بازکاری برگرداند. رد یا بازکاری بدون بازخورد اقدام‌پذیر معتبر نیست. تا وقتی همهٔ هفت بخش قرارداد (`charter`, `responsibilities`, `decision-rights`, `input`, `output`, `principles`, `workflow`) تأیید نشده‌اند، تیم آمادهٔ کار نیست.

## چرخهٔ عمر تیم

```text
proposed -> training -> ready -> assigned -> working -> review -> completed
                    |                         |          |
                    +------ rework <---------+----------+
                             |
                           paused
                             |
                          retired
```

`ready` فقط زمانی صادر می‌شود که قرارداد کامل تأیید و پنج ماژول آموزش با امتیاز حداقل ۸۰ گذرانده شده باشد. `retired` به معنی حذف نیست؛ سابقه و Eventهای تیم حفظ می‌شود و فقط از تخصیص جدید جلوگیری می‌کند.

## کنترل انسانی

مالک پروژه از اتاق کنترل یا API می‌تواند:

1. فهرست و جزئیات هر تیم، وضعیت قرارداد، آموزش، تخصیص و بازکاری را ببیند؛
2. هر بخش قرارداد را `approved` یا `rejected` کند؛
3. برای قرارداد یا خروجی پروژه `rework-requested` ثبت کند؛
4. ورودی یا خروجی یک پروژه را با شناسهٔ Artifact و نسخه تأیید یا رد کند؛
5. تیم آماده را به مرحله و Task مشخص تخصیص دهد؛
6. برای هر مرحله سطح خودکارسازی را تغییر دهد؛
7. فلو همکاری یک پروژه را بازتعریف کند؛
8. تیم‌ها را ادغام یا یک تیم را تفکیک کند، بدون از بین بردن تاریخچهٔ قبلی.

تمام تغییرات بالا Event نسخه‌دار و append-only دارند. تغییر اختیار تیم به‌تنهایی مجوز Production، Secret، هزینه، پیام خارجی یا عملیات برگشت‌ناپذیر نیست.

## سطح خودکارسازی

| حالت | رفتار |
| --- | --- |
| `owner-gated` | تیم پیش از هر اقدام/خروجی منتظر تصمیم مالک می‌ماند. |
| `stage-gated` | تیم در محدودهٔ مرحلهٔ تأییدشده خودکار کار می‌کند و در گیت خروجی متوقف می‌شود. |
| `autonomous-with-escalation` | تیم تا وقتی ابهام، ریسک یا اقدام خارج از قرارداد نبیند ادامه می‌دهد؛ در آن نقاط متوقف و ارجاع می‌دهد. |

این تنظیم دو لایه دارد: حالت پیش‌فرض تیم و override برای یک مرحلهٔ مشخص. علاوه بر آن، فلو پروژه برای هر مرحله یکی از `every-step`، `gate-only` یا `on-risk-only` را تعیین می‌کند. بنابراین «اختیار کامل» یک کلید مبهم نیست و دقیقاً معلوم است چه کسی، در کدام مرحله و تا کجا تصمیم می‌گیرد.

## فلو استاندارد شرکت

```text
مسئله
  -> راهبرو: ثبت و تعیین اختیار
  -> ایده‌پردازو + تحلیلگرو: کشف، شواهد و گزینه‌ها
  -> محصولو: PRD، MVP و معیار پذیرش
  -> دیزاینرو + معمارو: تجربه و معماری
  -> دولوپرو: پیاده‌سازی
  -> داده‌و: KPI و Instrumentation
  -> تسترو + امینتو: کیفیت و امنیت
  -> عملیاتو: محیط، پایش و بازیابی
  -> راهبرو + محصولو: تحویل، یادگیری و تصمیم تکرار
```

راهبرو ترتیب و گیت را مدیریت می‌کند، اما تأیید تخصصی محصول، امنیت، کیفیت و عملیات را جعل نمی‌کند. هر خروجی به‌صورت یک Task با یک مالک اصلی و وابستگی‌های مشخص در Planner قرار می‌گیرد.

پس از خروجی تسترو و امینتو، عملیاتو فقط Artifact نسخه‌دار و commitی را برای انتشار پیشنهاد می‌کند که در test آزموده شده است. مسیر دقیق Git → test → تأیید مالک → production در [RELEASE_FLOW.md](RELEASE_FLOW.md) تعریف شده و تولید یا استقرار زنده خارج از Registry deterministic فعلی است.

## API کنترل اولیه

- `GET /api/teams` فهرست، قرارداد و وضعیت عملیاتی تیم‌ها را می‌دهد.
- `POST /api/teams/:teamId/review` یک بخش قرارداد را تأیید یا رد می‌کند.
- `POST /api/teams/:teamId/rework` درخواست بازکاری قرارداد ثبت می‌کند.
- `POST /api/teams/:teamId/deliverable-review` ورودی/خروجی پروژه را بررسی می‌کند.
- `POST /api/teams/:teamId/autonomy` خودکارسازی یک مرحله را تغییر می‌دهد.
- `POST /api/teams/:teamId/training` نتیجهٔ یک ماژول آموزش را ثبت می‌کند.
- `POST /api/teams/:teamId/assign` تیم آماده را به Project/Stage/Task تخصیص می‌دهد.
- `POST /api/team-assignments/:assignmentId/update` وضعیت اجرای تخصیص را به‌روزرسانی می‌کند.
- `POST /api/projects/:projectId/team-workflow` فلو و approval mode تیمی پروژه را ثبت می‌کند.
- `POST /api/teams/merge` و `POST /api/teams/:teamId/split` تغییر ساختار تیمی را با حفظ تاریخچه ثبت می‌کنند.
- `GET /team-contract` خلاصهٔ قرارداد ماشینی را می‌دهد.

این API در وضعیت فعلی deterministic و in-memory است؛ PostgreSQL، صف پایدار، Provider واقعی و اجرای بیرونی هنوز آداپترهای جداگانهٔ آینده‌اند.

## تیم‌های مکمل پیشنهادی

برای «شرکت تحویل نرم‌افزار» همین ۱۱ تیم کافی‌اند. برای شبیه‌سازی کامل خود شرکت، سه قابلیت سازمانی در مرحلهٔ بعد پیشنهاد می‌شود:

- **توانمندسازو**: برنامهٔ آموزش، آزمون، رتبه‌بندی، ارزیابی و بهبود هر تیم؛ این قابلیت در مرحلهٔ اول به‌صورت کنترل داخلی Registry است.
- **رشد و پشتیبان**: بازخورد بازار، پشتیبانی کاربر، دسته‌بندی فرصت و تبدیل بازخورد به مسئلهٔ جدید.
- **مالی و حقوقی**: بودجه، هزینه، قرارداد، انطباق و بررسی تعهدات بیرونی؛ این تیم باید پشت گیت جداگانهٔ هزینه و اقدام خارجی بماند.

منابع انسانی و ظرفیت را فعلاً به توانمندسازو/راهبرو می‌سپاریم؛ اگر بعداً تیم‌ها اعضای متعدد، ظرفیت محدود یا نقش‌های انسانی پیدا کردند، آن را به تیم مستقل «منابع‌انسانی‌و» تفکیک می‌کنیم.
